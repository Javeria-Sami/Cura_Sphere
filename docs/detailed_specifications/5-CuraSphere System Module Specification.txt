4. SYSTEM MODULE SPECIFICATION
4.1 Purpose
The purpose of this section is to divide CuraSphere into clearly defined functional modules.
A software module represents a cohesive business capability or system responsibility.
CuraSphere shall not be treated as one large application containing unrelated features.
The system shall be decomposed into controlled modules.
                    CURASPHERE                         │                         ▼                 SYSTEM CAPABILITIES                         │                         ▼                 FUNCTIONAL DOMAINS                         │                         ▼                      MODULES                         │                         ▼                    SUBMODULES                         │                         ▼                     FEATURES                         │                         ▼                   REQUIREMENTS
The module decomposition shall help:
separate business responsibilities;
reduce system complexity;
improve maintainability;
support parallel development;
improve testability;
define API boundaries;
define data ownership;
support future scalability;
reduce unnecessary coupling.

4.2 Module Design Principles
CuraSphere modules shall follow the following principles.
4.2.1 Single Business Responsibility
Each module should represent a clear business capability.
Example:
Patient Module
is responsible for patient administrative information.
It should not become responsible for:
Billing calculationsMedicine inventoryUser authenticationDeployment configuration

4.2.2 High Cohesion
Related functionality shall remain within the same logical module.
Example:
Appointment Module├── Appointment Booking├── Appointment Rescheduling├── Appointment Cancellation├── Appointment Status└── Appointment History
These functions belong together.

4.2.3 Controlled Coupling
Modules may depend on other modules where required.
However, dependencies shall be explicit.
Example:
APPOINTMENT     │     ├────► PATIENT     │     └────► DOCTOR
An appointment requires a patient and a doctor.
The appointment module should not independently duplicate patient or doctor master information.

4.2.4 Data Ownership
Each major business concept shall have a logical owning module.
Example:
Business Information
Logical Owner
Patient demographic record
Patient Module
Appointment
Appointment Module
Clinical encounter
EMR/Clinical Module
Prescription
Prescription/Clinical Module
Medicine batch
Pharmacy Module
Laboratory result
Laboratory Module
Invoice
Billing Module
User account
Identity and Access Module
Other modules may use approved information without becoming its logical owner.

4.2.5 Authorization at Module Boundaries
A user’s access to one module shall not automatically provide access to every CuraSphere module.
Example:
RECEPTIONISTPatient Registration     ALLOWEDAppointment Booking      ALLOWEDClinical Diagnosis       NOT ALLOWEDLab Result Approval      NOT ALLOWEDRefund Approval          NOT ALLOWEDRole Management          NOT ALLOWED

4.2.6 Auditability
Sensitive module operations shall generate appropriate audit information.
Examples include:
permission changes;
clinical record changes;
laboratory result approval;
radiology report release;
refund processing;
stock adjustment.

4.3 CuraSphere Module Coding Convention
Every module shall have a short module code.
The module code shall be used in:
requirement IDs;
architecture documentation;
API documentation;
test documentation;
project planning;
issue tracking.
The format is:
CS-[MODULE]-[TYPE]-[NUMBER]
Example:
CS-PAT-FR-001
means:
CS      CuraSpherePAT     Patient ModuleFR      Functional Requirement001     Requirement Number

4.40 Module Interaction Rules
Rule 1 — No Uncontrolled Data Duplication
A module should not create its own independent copy of another module’s master information without a documented reason.
Example:
APT should reference PATIENTNOT duplicate:AppointmentPatientNameAppointmentPatientDOBAppointmentPatientAddressas an independent patient master record.
Historical snapshots may be permitted where business requirements require immutable historical information.

Rule 2 — Business Rules Remain with the Responsible Domain
Example:
Can this appointment be cancelled?
The Appointment domain should define the appointment cancellation rule.
The React UI should not become the only location containing this business rule.

Rule 3 — UI Is Not a Business Module
React pages are not domain modules.
Example:
PatientPage.jsx
is a UI implementation concept.
PAT — Patient Management
is a business module.

Rule 4 — Database Tables Do Not Define Modules
A table name does not automatically define the architecture.
Example:
patients
may store patient data.
However, the Patient module includes:
validation;
duplicate detection;
patient search;
MRN generation;
authorization;
business rules.
A module is larger than a database table.

Rule 5 — Module Communication Shall Be Explicit
When one module requires another module’s information, the dependency shall be documented.
Example:
APT │ ├──── requires valid PATIENT │ └──── requires valid DOCTOR
