7.2 Layered Enterprise Architecture

7.2.1 Introduction
The Layered Enterprise Architecture defines how the CuraSphere Hospital Management System is logically organized into independent architectural layers, each with a specific responsibility. This approach separates user interface concerns from business logic, integration services, data access, and infrastructure management, making the system easier to develop, test, deploy, secure, and maintain.
In a large-scale hospital environment, multiple users—including doctors, nurses, pharmacists, laboratory technicians, administrators, accountants, receptionists, and patients—may access the system simultaneously. To ensure reliability and scalability, requests flow through well-defined layers rather than allowing direct interaction between the user interface and the database.
The layered architecture minimizes coupling between components, promotes code reusability, and allows future enhancements without requiring significant modifications to unrelated modules.

7.2.2 Objectives
The Layered Enterprise Architecture shall:
Separate presentation from business logic.
Improve maintainability and readability.
Support independent module development.
Enable horizontal scalability.
Facilitate unit and integration testing.
Simplify deployment and updates.
Enhance security by isolating responsibilities.
Improve interoperability with external systems.
Support cloud-native deployments.
Ensure consistent communication between all modules.

7.2.12 Layer 2 — Authentication & Authorization Layer

7.2.12.1 Introduction
The Authentication and Authorization Layer is responsible for ensuring that only authenticated and authorized users can access the CuraSphere Hospital Management System. Since the application stores confidential patient records, financial information, prescriptions, laboratory reports, diagnostic images, and administrative data, access control must be implemented at every level of the application.
This layer acts as the first security boundary after the Presentation Layer. Every incoming request shall pass through this layer before reaching the Business Service Layer.
The Authentication and Authorization Layer shall support enterprise identity management, session control, secure token validation, multi-factor authentication (MFA), role-based access control (RBAC), password policies, and audit logging.

7.2.12.2 Objectives
The Authentication and Authorization Layer shall:
Verify user identity.
Authenticate users securely.
Prevent unauthorized access.
Enforce role-based permissions.
Support Multi-Factor Authentication (MFA).
Manage secure sessions.
Issue and validate JWT tokens.
Log authentication events.
Detect suspicious login activities.
Support future Single Sign-On (SSO).

7.2.15 Layer 5 — Integration Layer

7.2.15.1 Introduction
The Integration Layer enables CuraSphere to communicate securely and reliably with external systems, medical devices, government health services, insurance providers, payment gateways, notification providers, laboratory analyzers, radiology systems, and future third-party healthcare applications.
Hospitals rarely operate as isolated systems. Patient information often flows between laboratories, imaging centers, pharmacies, insurance companies, national health databases, and financial institutions. Therefore, the Integration Layer acts as a controlled gateway that isolates the core business services from external dependencies.
This layer ensures that changes to third-party systems do not directly affect the internal architecture of CuraSphere.

7.2.15.2 Objectives
The Integration Layer shall:
Integrate with external healthcare systems.
Provide standardized APIs.
Transform external data into internal formats.
Support secure communication.
Handle communication failures gracefully.
Retry temporary failures automatically.
Log all integration events.
Maintain interoperability with healthcare standards.

7.2.16 Layer 6 — Data Access Layer

7.2.16.1 Introduction
The Data Access Layer (DAL) provides controlled interaction with the PostgreSQL database. No application component other than the DAL shall directly execute SQL statements against the database.
This abstraction improves maintainability, testability, security, and consistency.

Responsibilities
The DAL shall:
Execute CRUD operations.
Manage database connections.
Handle transactions.
Execute stored procedures (where applicable).
Apply optimistic or pessimistic concurrency controls as needed.
Prevent SQL Injection through parameterized queries or ORM mechanisms.
Manage connection pooling.
Translate database exceptions into application exceptions.

Repositories encapsulate persistence logic for each aggregate or entity.
