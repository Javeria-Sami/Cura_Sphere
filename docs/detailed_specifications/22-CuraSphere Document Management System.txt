5.1193 DOCUMENT DOMAIN BOUNDARY
The DOC/FIL module shall manage document and file lifecycle processing.
It shall not own the clinical or business record represented by the document.
Example:
LABORATORY MODULE        │        ▼OWNS LAB RESULT
Document module:
DOC/FIL   │   ▼OWNS LAB RESULT ATTACHMENT FILE
Therefore:
LAB RESULT     ≠LAB ATTACHMENT
Another example:
RADIOLOGY MODULE       │       ▼OWNS RADIOLOGY REPORT
Document module:
DOC/FIL   │   ▼OWNS APPROVED REPORT DOCUMENT FILE
Another:
PATIENT MODULE      │      ▼OWNS PATIENT DEMOGRAPHICS
Document module:
DOC/FIL   │   ▼OWNS PATIENT IDENTITY DOCUMENT FILE
Critical Principle
BUSINESS / CLINICAL MODULE            │            ▼OWNS BUSINESS MEANING
DOC/FIL   │   ▼OWNS DOCUMENT AND FILE LIFECYCLE
The Document module shall not independently:
DIAGNOSE PATIENTSVERIFY LAB RESULTSAPPROVE RADIOLOGY REPORTSDISPENSE MEDICATIONCONFIRM APPOINTMENTSMARK INVOICES PAIDCHANGE PATIENT DEMOGRAPHICSAPPROVE EMPLOYEE LEAVE
because a file was uploaded, downloaded, archived, or versioned.

5.1194 DOCUMENT VS FILE CONCEPT
CuraSphere shall distinguish:
DOCUMENT
from:
FILE
A document represents the business-managed digital record.
Example:
DOCUMENTPATIENT REFERRAL LETTER
The file represents the binary digital object.
Example:
FILEreferral-letter.pdf
Conceptually:
DOCUMENT   │   ▼DOCUMENT METADATA   │   ▼FILE REFERENCE   │   ▼BINARY OBJECT
A document may later have multiple versions:
DOCUMENT   │   ├── VERSION 1   │       └── FILE A   │   ├── VERSION 2   │       └── FILE B   │   └── VERSION 3           └── FILE C
Therefore:
DOCUMENT ID     ≠FILE ID
and:
DOCUMENT VERSION       ≠DOCUMENT

5.1195 DOCUMENT STORAGE ARCHITECTURAL BOUNDARY
The SRS shall distinguish document metadata from binary file storage.
Conceptually:
POSTGRESQL    │    ▼DOCUMENT METADATA
Potential metadata:
DOCUMENT IDFILE IDDOCUMENT TYPEPATIENT REFERENCEBUSINESS REFERENCEFILE SIZEMEDIA TYPECHECKSUMSTORAGE PROVIDERSTORAGE KEYSTATUSCREATED TIME
Binary content:
PDF BYTESIMAGE BYTESSCANNED DOCUMENT BYTES
shall be managed through an approved storage boundary.
Conceptually:
ASP.NET CORE APPLICATION          │          ▼DOCUMENT SERVICE          │          ▼FILE STORAGE ABSTRACTION          │    ┌─────┼──────────┐    │     │          │    ▼     ▼          ▼ LOCAL   OBJECT     CLOUDSTORAGE  STORAGE   STORAGE
This SRS shall not require every large file to be stored directly as PostgreSQL binary data.
Critical Principle
POSTGRESQL    │    ▼DOCUMENT METADATA + REFERENCES
APPROVED FILE STORAGE          │          ▼BINARY CONTENT
The final physical storage technology shall be selected during Data, Infrastructure, Security, and Detailed Architecture.

5.1196 REACT PUBLIC FOLDER BOUNDARY
Patient and hospital documents shall not be treated as public frontend assets.
Incorrect:
React Application      │      ▼public/   ├── patient-001-lab.pdf   ├── patient-002-scan.jpg   └── prescription-009.pdf
This may expose documents through predictable public URLs.
Preferred boundary:
REACT CLIENT     │     ▼AUTHORIZED API REQUEST     │     ▼ASP.NET CORE API     │     ▼AUTHORIZATION     │     ▼DOCUMENT ACCESS POLICY     │     ▼FILE STORAGE
Therefore:
UI ASSET   ≠PATIENT DOCUMENT
The React public folder may contain approved public application assets such as:
LOGOPUBLIC ICONSTATIC BRAND IMAGE
It shall not become the hospital document repository.

5.1199 REGISTER DOCUMENT

The system shall allow authorized users and approved CuraSphere modules to register a document.
Main flow:
AUTHORIZED ACTOR / MODULE          │          ▼CREATE DOCUMENT REQUEST          │          ▼SELECT DOCUMENT TYPE          │          ▼IDENTIFY SOURCE          │          ▼ASSOCIATE BUSINESS RECORD          │          ▼UPLOAD FILE          │          ▼VALIDATE          │          ▼STORE          │          ▼REGISTER DOCUMENT
Potential registration information includes:
DOCUMENT TYPEDOCUMENT CATEGORYSOURCESOURCE MODULEPATIENT REFERENCEENCOUNTER REFERENCEBUSINESS REFERENCEFILEDESCRIPTIONSENSITIVITY CLASSIFICATION
The system shall reject incomplete document registration where mandatory associations are missing.

Therefore:
ORIGINAL FILE NAME         ≠STORAGE KEY

5.1214 SAFE STORAGE NAME
CS-DOC-FR-016 — Generate Safe Storage Name
The system shall generate or assign a safe storage identifier or key.
Example:
STORAGE KEYhospital-a/2026/07/fil-000009521
The system shall not rely on:
../../patient-files/report.pdf
or other unsafe user-provided path values.
Storage naming shall be controlled by the server.

5.1215 FILE NAME VALIDATION
CS-DOC-FR-017 — Validate File Name
The system shall validate uploaded file names.
The validation shall consider:
EMPTY FILE NAMEEXCESSIVE LENGTHCONTROL CHARACTERSPATH SEPARATORSPATH TRAVERSAL PATTERNSUNSAFE CHARACTERS
Example unsafe value:
../../../../system/config.json
The server shall not use this value directly as a physical path.

5.1216 FILE EXTENSION VALIDATION
CS-DOC-FR-018 — Validate File Extension
The system shall validate file extensions according to approved document policy.
Potential approved extensions may include:
.pdf.jpg.jpeg.png
Additional formats shall require approval.
An extension allowlist shall be preferred over unrestricted upload.
Example:
malware.exe
Result:
FILE TYPE NOT ALLOWED
The final extension matrix shall be defined during Security and Detailed Design.

5.1217 MEDIA TYPE VALIDATION
CS-DOC-FR-019 — Validate Media Type
The system shall validate the media type of uploaded files.
Example:
application/pdfimage/jpegimage/png
The system shall not rely only on:
Content-Type
provided by the client.
Client-provided metadata shall be treated as untrusted input.

5.1222 FILE INTEGRITY VERIFICATION

The system shall support file integrity verification.
Conceptually:
STORED FILE     │     ▼CALCULATE CHECKSUM     │     ▼COMPARE WITH REGISTERED CHECKSUM     │  ┌──┴───┐  │      │MATCH  MISMATCH  │      │  ▼      ▼VALID   INTEGRITY FAILURE
A checksum mismatch shall be treated as an operational or security event according to approved policy.

5.1223 DUPLICATE FILE DETECTION
CS-DOC-FR-025 — Detect Eligible Duplicate File
The system shall support duplicate file detection where required.
Potential signals include:
CHECKSUMFILE SIZEDOCUMENT TYPEBUSINESS REFERENCEPATIENT REFERENCE
The same checksum shall not automatically mean:
DELETE DUPLICATE
because the same document may be legitimately associated with multiple records.
Duplicate detection shall support review or approved deduplication policies.

The system shall not assume:
.pdf
means:
SAFE

5.1225 QUARANTINE UNSAFE FILE
CS-DOC-FR-027 — Quarantine Unsafe File
The system shall quarantine files classified as unsafe or requiring security review.
Conceptually:
FILE │ ▼MALWARE / SECURITY CHECK │ ▼UNSAFE │ ▼QUARANTINED
A quarantined file shall not be available through normal document download workflows.
The file shall not be treated as an active clinical document.

5.1226 RELEASE QUARANTINED FILE

5.1295 DOCUMENT AND FILE MANAGEMENT RISK ANALYSIS
Risk 1 — Patient Files Stored in React Public Folder
Problem
frontend/public/patients/
contains medical documents.
Impact
Files may become directly accessible through public URLs.
Mitigation
Use authorized API and protected storage boundaries.

Risk 2 — Large Files Stored Randomly in PostgreSQL
Problem
Every PDF, image, and scan is inserted directly into general application tables without storage architecture.
Impact
Database growth, backup complexity, restore complexity, and operational problems increase.
Mitigation
Separate document metadata from approved binary storage.

Risk 3 — Physical File Paths Stored Everywhere
Problem
C:\HospitalFiles\Patients\108\report.pdf
is used inside controllers and business services.
Impact
Storage migration becomes difficult.
Mitigation
Use storage abstraction and controlled storage references.

Risk 4 — User File Name Becomes Server Path
Problem
Uploaded name:
../../config/appsettings.json
is used directly.
Impact
Path traversal and file overwrite risk.
Mitigation
Generate server-controlled storage keys.

Risk 5 — Extension Is Trusted
Problem
virus.exe
is renamed:
report.pdf
Impact
Unsafe content may enter the document repository.
Mitigation
Validate extension, media type, and eligible file content characteristics.

Risk 6 — No File Size Limit
Problem
User uploads:
100 GB FILE
Impact
Storage exhaustion and denial of service.
Mitigation
Apply file size limits.

Risk 7 — Unlimited Files Per Request
Problem
One HTTP request contains 50,000 files.
Impact
Application memory and processing resources are exhausted.
Mitigation
Apply upload count limits and dedicated batch workflows.

Risk 8 — No Malware Scanning Boundary
Problem
Hospital staff upload externally received files directly into active document storage.
Impact
Malicious files may spread through hospital workflows.
Mitigation
Use approved malware scanning and quarantine boundaries.

Risk 9 — Quarantined File Can Still Be Downloaded
Problem
Status:
QUARANTINED
but normal download endpoint ignores status.
Impact
Unsafe files remain accessible.
Mitigation
Enforce file security state during retrieval.

Risk 10 — Document ID Grants Access
Problem
User changes:
DOC-0004821
to:
DOC-0004822
and downloads another patient’s document.
Impact
Medical information exposure.
Mitigation
Enforce permission and record scope on every document request.

Risk 11 — Receptionist Can Download Every Clinical Document
Problem
Generic permission:
DOC_VIEW
grants access to every document.
Impact
Clinical confidentiality boundaries are lost.
Mitigation
Use category, business scope, and sensitivity-aware authorization.

Risk 12 — Document Administrator Becomes Clinical Superuser
Problem
Storage administration permission grants access to all patient files.
Impact
Technical privilege becomes clinical privilege.
Mitigation
Separate document administration from document-content authorization.

Risk 13 — New Upload Overwrites Old Document
Problem
Corrected report replaces the original binary file.
Impact
Historical evidence is lost.
Mitigation
Use document versioning.

Risk 14 — Client Controls Version Number
Problem
Client sends:
version = 100
Impact
Document history becomes inconsistent.
Mitigation
The server shall manage version sequencing.

Risk 15 — Superseded Version Is Deleted
Problem
Version 2 becomes current.
Version 1 is physically deleted immediately.
Impact
Historical traceability is lost.
Mitigation
Preserve required historical versions.

Risk 16 — Review Equals Clinical Verification
Problem
Document administrator checks file readability.
The system marks:
CLINICALLY VERIFIED
Impact
Administrative review is misrepresented as clinical verification.
Mitigation
Separate document review and clinical verification concepts.

Risk 17 — Delete Button Permanently Removes Medical Record
Problem
Normal user clicks:
DELETE
and the file is physically destroyed.
Impact
Retention, legal, and clinical record obligations may be violated.
Mitigation
Use controlled soft deletion and retention policies.

Risk 18 — Legal Hold Is Ignored
Problem
Retention cleanup deletes a document under legal investigation.
Impact
Required evidence may be destroyed.
Mitigation
Apply legal hold before permanent deletion.

Risk 19 — Search Reveals Restricted File Names
Problem
User cannot open a document but search results show:
HIV-Positive-Report.pdf
Impact
Sensitive information leaks through metadata.
Mitigation
Apply authorization before search-result exposure.

Risk 20 — Internal Storage Path Returned to React
Problem
API returns:
C:\HospitalStorage\Patients\108\report.pdf
Impact
Infrastructure details are exposed.
Mitigation
Return document identifiers and approved metadata only.

Risk 21 — Entire File Loaded Into Memory
Problem
A large file is loaded as one byte array for every download.
Impact
Application memory pressure increases.
Mitigation
Use streaming where appropriate.

Risk 22 — Database Backup Excludes File Storage
Problem
PostgreSQL is backed up.
Object storage is not.
Impact
Restored database references files that no longer exist.
Mitigation
Coordinate metadata and binary backup strategies.

Risk 23 — File Storage Restored From Different Date
Problem
Database and storage recovery points are inconsistent.
Impact
Missing and orphan files appear.
Mitigation
Define recovery consistency and reconciliation.

Risk 24 — Orphan Files Are Deleted Immediately
Problem
Storage scan finds an unreferenced file and deletes it.
Impact
A temporary transaction or migration issue may cause legitimate data loss.
Mitigation
Use controlled orphan reconciliation.

Risk 25 — Missing File Is Hidden
Problem
Metadata exists but binary content is missing.
The UI repeatedly returns generic:
ERROR
Impact
Operational corruption remains undetected.
Mitigation
Detect and monitor metadata-file consistency failures.

Risk 26 — Checksum Mismatch Is Ignored
Problem
Stored file content changes unexpectedly.
Impact
Document integrity may be compromised.
Mitigation
Support checksum verification and security event recording.

Risk 27 — OCR Text Is Treated as Clinical Truth
Problem
OCR reads:
10 mg
as:
100 mg
The extracted value is automatically inserted into a prescription.
Impact
Patient safety may be affected.
Mitigation
OCR output shall not automatically become verified clinical data.

Risk 28 — Search Index Bypasses Document Security
Problem
Users cannot open a document but can search all extracted text.
Impact
Sensitive clinical content is exposed.
Mitigation
Apply document authorization to content search.

Risk 29 — Typed Name Is Treated as Universal Legal Signature
Problem
User types:
Ali Khan
The system declares the document legally digitally signed.
Impact
Legal validity may be misrepresented.
Mitigation
Define electronic and digital signature requirements through legal review.

Risk 30 — DICOM Images Stored Like Normal PDFs
Problem
Large imaging studies are uploaded through the ordinary document attachment endpoint.
Impact
Storage, transfer, metadata, and clinical imaging workflows become unsuitable.
Mitigation
Preserve a separate DICOM/PACS architecture boundary.

Risk 31 — Patient Upload Automatically Becomes Verified Record
Problem
Patient uploads an external report.
The system marks:
VERIFIED CLINICAL DOCUMENT
Impact
Unreviewed external content becomes official hospital information.
Mitigation
Require approved review or verification workflows.

Risk 32 — Document Microservice Created Too Early
Problem
The RAD team immediately creates:
DOCUMENT MICROSERVICEFILE MICROSERVICESTORAGE MICROSERVICEOCR MICROSERVICESIGNATURE MICROSERVICE
Impact
DISTRIBUTED TRANSACTIONSORPHAN FILE COMPLEXITYNETWORK FAILURE MODESDEPLOYMENT COMPLEXITYDEVOPS OVERHEAD
Mitigation
Begin with a well-isolated modular document domain and storage abstraction.
Extract independent services only when architectural evidence requires them.
