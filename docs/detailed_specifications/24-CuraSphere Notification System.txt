5.1429 NOTIFICATION DOMAIN BOUNDARY
The NTF/COM module shall own notification and communication processing.
The source business module shall own the business event.
Example:
APPOINTMENT MODULE        │        ▼OWNS APPOINTMENT
When appointment is cancelled:
APPOINTMENT MODULE        │        ▼APPOINTMENT_CANCELLED
NTF/COM:
NTF/COM   │   ▼RESOLVE RECIPIENT   │   ▼CREATE NOTIFICATION   │   ▼DELIVER APPROVED COMMUNICATION
Another example:
BILLING MODULE      │      ▼OWNS PAYMENT
Payment event:
PAYMENT_RECEIVED
NTF/COM:
PAYMENT_RECEIVED       │       ▼PAYMENT CONFIRMATION NOTIFICATION
Critical Principle
SOURCE MODULE      │      ▼OWNS BUSINESS FACT
NTF/COM   │   ▼OWNS COMMUNICATION PROCESS
Therefore:
NOTIFICATION     ≠BUSINESS TRANSACTION
A notification marked:
DELIVERED
shall not automatically mean:
APPOINTMENT COMPLETED
or:
PAYMENT CONFIRMED IN FINANCIAL LEDGER
or:
LAB RESULT CLINICALLY VERIFIED

5.1430 COMMUNICATION INFRASTRUCTURE BOUNDARY
Operational modules shall not independently implement communication-provider infrastructure.
Incorrect architecture:
APPOINTMENT CONTROLLER        │        ▼SMTP CLIENT        │        ▼EMAIL PROVIDER
Another incorrect architecture:
BILLING SERVICE      │      ▼SMS PROVIDER SDK
Another:
LAB SERVICE    │    ▼HARDCODED EMAIL PASSWORD
Preferred architecture:
SOURCE MODULE      │      ▼BUSINESS EVENT      │      ▼NTF/COM      │      ▼COMMUNICATION ABSTRACTION      │      ▼CHANNEL PROVIDER
Therefore:
APPOINTMENTBILLINGLABRADIOLOGYPHARMACYHRREPORTING
shall communicate through approved NTF/COM boundaries.
Critical Principle
BUSINESS MODULE       ≠EMAIL / SMS INFRASTRUCTURE OWNER

DECIDE AUTHORITATIVE RECIPIENTSDIRECTLY CALL SMS PROVIDERDIRECTLY CALL EMAIL PROVIDERSTORE SMTP PASSWORDSTORE SMS API SECRETCALCULATE MANDATORY COMMUNICATION POLICYBYPASS QUIET-HOUR POLICYGENERATE SECURITY ALERTS LOCALLY AS AUTHORITATIVE EVENTS

5.1434 CREATE NOTIFICATION EVENT
CS-NTF-FR-001 — Create Notification Event
The system shall allow approved source modules to create or publish eligible notification events.
Example:
APPOINTMENT_CANCELLED
Another:
PAYMENT_RECEIVED
Another:
LAB_RESULT_AVAILABLE
The notification event shall represent a communication-relevant business or system occurrence.
Conceptually:
BUSINESS FACT     │     ▼SOURCE MODULE     │     ▼NOTIFICATION EVENT
The notification event shall not replace the source business record.

5.1435 NOTIFICATION EVENT IDENTIFIER
CS-NTF-FR-002 — Generate Notification Event Identifier
The system shall assign a unique identifier to eligible notification events.
Example:
NTF-EVT-00098211
The event identifier shall support:
TRACEABILITYIDEMPOTENCYDUPLICATE DETECTIONPROCESSING HISTORY
The event identifier shall remain distinct from the generated notification identifier.
Therefore:
EVENT ID   ≠NOTIFICATION ID

5.1438 NOTIFICATION EVENT VALIDATION

The system shall validate eligible notification events before processing.
Validation may include:
EVENT TYPEEVENT IDENTIFIERSOURCE MODULESOURCE REFERENCEREQUIRED CONTEXTEVENT TIMESCHEMA VERSION BOUNDARY
Invalid events shall not automatically proceed to communication delivery.

5.1439 DUPLICATE EVENT PROCESSING PREVENTION
CS-NTF-FR-006 — Prevent Duplicate Event Processing
The system shall prevent accidental duplicate processing of the same eligible event.
Example:
NTF-EVT-00098211
received twice.
Incorrect:
FIRST EVENT    │    ▼SEND SMSSECOND COPY    │    ▼SEND SAME SMS AGAIN
Preferred:
EVENT ID   │   ▼ALREADY PROCESSED?   │ ┌─┴─┐ │   │YES  NO │   │ ▼   ▼SKIP PROCESS
The exact idempotency storage strategy shall be defined during Application and Data Architecture.

React shall not independently upgrade:
NOTICE
to:
CRITICAL
based solely on frontend logic.

5.1580 NOTIFICATION AND COMMUNICATION RISK ANALYSIS
Risk 1 — Every Module Implements Its Own Email Service
Problem
APPOINTMENT EMAIL SERVICELAB EMAIL SERVICEBILLING EMAIL SERVICEHR EMAIL SERVICE
Impact
Duplicate code, inconsistent security, and difficult provider migration.
Mitigation
Centralize communication processing through NTF/COM.

Risk 2 — SMS Provider Secret Stored in React
Problem
React contains:
SMS_API_KEY
Impact
The secret can be exposed to browser users.
Mitigation
Keep communication-provider secrets server-side.

Risk 3 — Business Transaction Waits for SMS Provider
Problem
Patient books appointment.
The HTTP request waits 30 seconds for SMS delivery.
Impact
Appointment workflow appears broken.
Mitigation
Separate eligible notification delivery from the core transaction through background processing.

Risk 4 — Notification Delivery Changes Business State
Problem
Payment notification is delivered.
System marks invoice paid.
Impact
Communication infrastructure becomes a financial source of truth.
Mitigation
Keep Billing as the owner of payment and invoice state.

Risk 5 — Duplicate Event Creates Duplicate SMS Messages
Problem
The same event is processed five times.
Impact
Patient receives five identical reminders.
Mitigation
Use event idempotency and duplicate-notification prevention.

Risk 6 — Retry Creates Duplicate Delivery
Problem
Provider accepts SMS but response times out.
System immediately sends another SMS.
Impact
Patient receives duplicate messages.
Mitigation
Preserve delivery idempotency and evaluate provider delivery uncertainty.

Risk 7 — Arbitrary Recipient ID From React
Problem
Client changes:
recipientId = USER_A
to:
recipientId = USER_B
Impact
Unauthorized communication may be created.
Mitigation
Resolve recipients server-side.

Risk 8 — Patient Reads Another Patient’s Notification
Problem
Patient changes notification ID.
Impact
Private communication is exposed.
Mitigation
Enforce notification record scope on every request.

Risk 9 — Full Clinical Result Sent by SMS
Problem
Sensitive clinical result appears on a lock screen.
Impact
Privacy exposure.
Mitigation
Use minimum-information communication and secure CuraSphere access.

Risk 10 — Sensitive Document Attached to Ordinary Email
Problem
Medical document is sent as an unrestricted attachment.
Impact
Sensitive data leaves controlled application access.
Mitigation
Use secure access notifications where appropriate.

Risk 11 — Template Receives Complete Patient Entity
Problem
Template engine receives every patient field.
Impact
Unnecessary sensitive information becomes available to communication code.
Mitigation
Use explicit approved template variables.

Risk 12 — Missing Template Variable Is Sent to User
Problem
Patient receives:
Hello {{PATIENT_NAME}}
Impact
Communication quality and trust decline.
Mitigation
Validate variables before rendering.

Risk 13 — Template Change Has No History
Problem
A message causes a complaint.
Current template content differs from the delivered content.
Impact
The historical communication cannot be reconstructed.
Mitigation
Support template version traceability.

Risk 14 — User Disables Security Alerts
Problem
User disables all notifications.
Account compromise alert is suppressed.
Impact
Important security communication is lost.
Mitigation
Separate optional and mandatory notification categories.

Risk 15 — Quiet Hours Delay Emergency Alert
Problem
Emergency alert occurs at 02:00.
Quiet-hour policy delays it until 07:00.
Impact
Critical operational response is delayed.
Mitigation
Support governed emergency override.

Risk 16 — Everyone Can Send Hospital-Wide Notifications
Problem
Ordinary staff user can notify every employee.
Impact
Abuse, confusion, and communication flooding.
Mitigation
Separate hospital and mass-communication permissions.

Risk 17 — Cross-Hospital Notification Scope Is Trusted From Client
Problem
Hospital A user selects Hospital B.
Impact
Unauthorized communication crosses organizational boundaries.
Mitigation
Validate hospital communication scope server-side.

Risk 18 — Notification Flooding
Problem
A software defect creates millions of notifications.
Impact
Database, queue, provider, and recipients are overloaded.
Mitigation
Use rate limits, throttling, monitoring, and operational alerts.

Risk 19 — Application Restart Loses Notifications
Problem
Notification work exists only in memory.
Impact
Important reminders disappear after deployment or crash.
Mitigation
Preserve durable processing boundaries.

Risk 20 — Poison Message Crashes Worker Forever
Problem
One invalid message repeatedly crashes processing.
Impact
The worker remains unstable and other notifications may be delayed.
Mitigation
Use retry limits and dead-letter or isolation boundaries.

Risk 21 — Infinite Retry
Problem
Invalid phone number retries forever.
Impact
Resources and provider capacity are wasted.
Mitigation
Classify failure and centrally govern retry eligibility.

Risk 22 — Provider Accepted Is Displayed as Read
Problem
SMS provider accepts the message.
CuraSphere displays:
PATIENT READ MESSAGE
Impact
Delivery semantics are incorrect.
Mitigation
Distinguish provider acceptance, delivery, read, and acknowledgement.

Risk 23 — React Calculates Unread Count From Current Page
Problem
React loads 20 notifications.
Four are unread.
UI displays:
4 UNREAD
Actual unread notifications:
87
Impact
User receives incorrect notification state.
Mitigation
Return authoritative unread count from the server.

Risk 24 — Scheduled Reminder Ignores Appointment Cancellation
Problem
Reminder is scheduled Monday.
Appointment is cancelled Tuesday.
Reminder is sent Wednesday.
Impact
Patient receives incorrect communication.
Mitigation
Revalidate scheduled notifications before delivery.

Risk 25 — Secure Link Never Expires
Problem
Email link remains valid forever.
Impact
Old forwarded or exposed links may remain usable.
Mitigation
Use expiration and target-resource authorization.

Risk 26 — Secure Link Replaces Authorization
Problem
Anyone with a link can access the complete patient record.
Impact
Resource authorization is bypassed.
Mitigation
Treat secure links as one access component, not universal authorization.

Risk 27 — Provider Raw Response Stored With Secrets
Problem
Provider response includes sensitive technical values.
The complete response is logged.
Impact
Secrets may enter logs.
Mitigation
Normalize provider responses and apply logging restrictions.

Risk 28 — Notification Logs Contain Full Clinical Messages
Problem
Every rendered message is written to application logs.
Impact
Sensitive clinical information spreads into log infrastructure.
Mitigation
Use privacy-aware logging boundaries.

Risk 29 — Provider Outage Is Invisible
Problem
SMS provider fails for eight hours.
No monitoring exists.
Impact
Thousands of notifications remain undelivered.
Mitigation
Monitor provider health and failed deliveries.

Risk 30 — Notification Admin Becomes Hospital Superuser
Problem
Template administrator can edit patient records and financial records.
Impact
Communication administration becomes universal business authority.
Mitigation
Separate notification permissions from domain permissions.

Risk 31 — Kafka Is Added on Day One Without Need
Problem
RAD team creates distributed event infrastructure before the modular system exists.
Impact
Operational and DevOps complexity increases.
Mitigation
Preserve event-driven boundaries but adopt broker infrastructure only when justified.

Risk 32 — One Notification Microservice Per Channel
Problem
The team immediately creates:
EMAIL MICROSERVICESMS MICROSERVICEPUSH MICROSERVICETEMPLATE MICROSERVICEPREFERENCE MICROSERVICENOTIFICATION MICROSERVICE
Impact
Deployment and distributed-system complexity increase.
Mitigation
Begin with a modular notification domain and provider abstractions.

Risk 33 — Mass Communication Uses Normal Notification Permission
Problem
A user who can send one workflow notification can send 100,000 messages.
Impact
Large-scale abuse becomes possible.
Mitigation
Use separate mass-communication authorization.

Risk 34 — AI Sends Clinical Communication Without Validation
Problem
AI generates a clinical message.
The system sends it automatically.
Impact
Incorrect or unsafe clinical information may be communicated.
Mitigation
Require domain, policy, and safety validation for AI-assisted communication.
