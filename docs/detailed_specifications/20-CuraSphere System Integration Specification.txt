5.995 INTEGRATION DOMAIN BOUNDARY
The INT/API module shall manage communication and interoperability boundaries.
It shall not become the owner of all data exchanged through integrations.
Example:
PATIENT MODULE      │      ▼OWNS PATIENT
Integration module:
INT/API   │   ▼TRANSPORTS / MAPS PATIENT DATA
Therefore:
PATIENT DATA TRANSPORT          ≠PATIENT OWNERSHIP
Another example:
BILLING MODULE      │      ▼OWNS PAYMENT TRANSACTION
Payment provider integration:
INT/API   │   ▼COMMUNICATES WITH PAYMENT PROVIDER
Therefore:
PAYMENT PROVIDER COMMUNICATION              ≠PAYMENT DOMAIN OWNERSHIP
Another example:
LABORATORY MODULE        │        ▼OWNS LAB ORDER AND RESULT
Laboratory device integration:
INT/API   │   ▼RECEIVES / TRANSMITS LAB DATA
Therefore:
LAB INTEGRATION       ≠LABORATORY BUSINESS DOMAIN
Critical Principle
DOMAIN MODULE      │      ▼OWNS BUSINESS MEANING
INTEGRATION MODULE         │         ▼OWNS COMMUNICATION BOUNDARY
The Integration module shall not independently:
DIAGNOSE PATIENTSAPPROVE LAB RESULTSFINALIZE RADIOLOGY REPORTSDISPENSE MEDICINESGENERATE SALARIESAPPROVE INSURANCE CLAIMSREVERSE PAYMENTSCREATE CLINICAL DECISIONS
unless the responsible domain service explicitly performs the business operation.

5.996 CRITICAL API ARCHITECTURE PRINCIPLE
CuraSphere shall distinguish:
API
from:
DOMAIN LOGIC
from:
DATABASE
Incorrect architecture:
REACT  │  ▼API CONTROLLER  │  ▼DIRECT SQL
Example:
[HttpPost]public IActionResult CreateAppointment(AppointmentDto dto){    // validate everything here    // calculate everything here    // execute SQL here    // send SMS here    // write audit here    // return response}
This architecture shall be avoided.
Preferred conceptual architecture:
REACT  │  ▼API ENDPOINT  │  ▼APPLICATION SERVICE  │  ▼DOMAIN RULES  │  ▼REPOSITORY / DATA ACCESS BOUNDARY  │  ▼POSTGRESQL
External communication:
APPLICATION SERVICE        │        ▼INTEGRATION ABSTRACTION        │        ▼EXTERNAL PROVIDER ADAPTER        │        ▼EXTERNAL SYSTEM
Therefore:
API CONTROLLER      ≠BUSINESS DOMAIN
and:
EXTERNAL PROVIDER SDK          ≠APPLICATION BUSINESS LOGIC

5.1001 INTERNAL APPLICATION API
CS-INT-FR-001 — Expose Internal Application API
CuraSphere shall expose approved application functionality through controlled ASP.NET Core API endpoints.
Conceptually:
REACT APPLICATION       │       ▼HTTPS       │       ▼ASP.NET CORE API       │       ▼APPLICATION LAYER       │       ▼DOMAIN
Example conceptual endpoint:
POST /api/appointments
The endpoint may request appointment creation.
However:
POST /api/appointments
shall not mean:
DIRECT INSERT INTO appointments
The responsible application and domain rules shall execute.

5.1002 REACT API CONSUMPTION
CS-INT-FR-002 — Support React API Consumption
The React application shall consume approved CuraSphere APIs.
Conceptually:
REACT COMPONENT      │      ▼UI ACTION      │      ▼CLIENT APPLICATION SERVICE      │      ▼API CLIENT      │      ▼ASP.NET CORE API
The architecture should avoid:
EVERY REACT COMPONENT          │          ▼CREATES RANDOM FETCH REQUESTS
Preferred:
REACT UI   │   ▼FEATURE / API LAYER   │   ▼CENTRAL API CLIENT
The final React data-fetching architecture shall be defined during UI Architecture.

5.1003 API CONSUMER AUTHENTICATION
CS-INT-FR-003 — Authenticate API Consumer
The system shall authenticate protected API consumers.
Conceptually:
API REQUEST     │     ▼AUTHENTICATION     │  ┌──┴──┐  │     │VALID INVALID  │     │  ▼     ▼CONTINUE REJECT
Authentication mechanisms may differ between:
HUMAN USER CLIENTINTERNAL SERVICEEXTERNAL PARTNERWEBHOOK PROVIDER
The final mechanisms shall be defined during IAM and Security Architecture.

5.1004 API REQUEST AUTHORIZATION
CS-INT-FR-004 — Authorize API Request
The system shall authorize protected API requests.
Example:
AUTHENTICATED USER        │        ▼POST /api/payments/{id}/reverse
Authentication alone shall not allow payment reversal.
The system shall verify:
PERMISSIONDATA SCOPEDOMAIN RULES
Conceptually:
AUTHENTICATED      │      ▼AUTHORIZED?   ┌──┴──┐   │     │  YES    NO   │     │   ▼     ▼PROCESS REJECT

5.1005 API REQUEST VALIDATION
CS-INT-FR-005 — Validate API Request
The API shall validate incoming requests.
Validation may include:
REQUIRED FIELDDATA TYPESTRING LENGTHNUMBER RANGEDATE FORMATENUM VALUEIDENTIFIER FORMATCOLLECTION SIZEDOMAIN REFERENCE
Example:
{  "pageSize": -500}
Result:
VALIDATION FAILURE
React validation may improve user experience.
ASP.NET Core shall enforce authoritative server validation.

5.1006 STANDARD API RESPONSE
CS-INT-FR-006 — Standardize API Response
CuraSphere shall define consistent API response conventions.
Successful resource example:
{  "id": "APT-000421",  "status": "SCHEDULED"}
Collection response may conceptually contain:
{  "items": [],  "page": 1,  "pageSize": 25,  "totalCount": 0}
The final API envelope strategy shall be defined during API Architecture.
The SRS does not require every successful response to be unnecessarily wrapped in:
{  "success": true,  "message": "Success",  "data": {}}
The final response standard shall follow REST and application architecture decisions.

The API shall provide standardized machine-readable errors.
Potential error information includes:
ERROR CODETITLEDETAILVALIDATION ERRORSCORRELATION ID

{  "code": "APPOINTMENT_SLOT_UNAVAILABLE",  "title": "Appointment slot unavailable",  "correlationId": "COR-8F72A1"}

to normal clients.

CLIENT FILTER     │     ▼DIRECT SQL WHERE STRING

5.1015 API SEARCH CONTRACTS

The system shall support approved search contracts.
Example:
GET /api/patients?search=uzair

Search behavior shall be domain-specific.
Patient search may consider:
PATIENT REFERENCEAPPROVED NAME FIELDSAPPROVED CONTACT FIELD
Inventory search may consider:
ITEM CODEITEM NAME
One universal search algorithm shall not be assumed for every domain.

5.1016 UNAUTHORIZED FIELD EXPOSURE PROTECTION
CS-INT-FR-016 — Prevent Unauthorized Field Exposure
The API shall prevent unauthorized data fields from being returned.
Example patient object contains:
PATIENT IDNAMECONTACTCLINICAL DATAFINANCIAL DATA
Reception endpoint requires:
PATIENT IDNAMECONTACT
The API shall not automatically return the complete patient aggregate.
Conceptually:
DOMAIN MODEL      │      ▼API RESPONSE CONTRACT      │      ▼AUTHORIZED FIELDS
The system shall not use database entities as unrestricted public API contracts.

5.1017 MASS ASSIGNMENT PROTECTION
CS-INT-FR-017 — Prevent Mass Assignment
The API shall prevent clients from updating unauthorized fields.
Example request:
{  "name": "Patient Name",  "isSystemAdministrator": true}
A patient update endpoint shall not bind:
isSystemAdministrator
to an internal security entity.
Preferred:
SPECIFIC REQUEST DTO
Example:
UpdatePatientContactRequest
containing only approved editable fields.

5.1019 API IDEMPOTENCY
CS-INT-FR-019 — Support API Idempotency
The system shall support idempotency for eligible operations.
Example:
CREATE PAYMENT REQUEST
Network timeout occurs.
Client retries.
Without idempotency:
REQUEST 1   │   ▼PAYMENT CREATED
REQUEST 2   │   ▼SECOND PAYMENT CREATED
Potential result:
DUPLICATE FINANCIAL TRANSACTION
Preferred:
IDEMPOTENCY KEY       │       ▼REQUEST 1       │       ▼PROCESS       │       ▼STORE RESULT
Retry:
SAME IDEMPOTENCY KEY          │          ▼EXISTING RESULT          │          ▼RETURN SAFE RESULT
Idempotency requirements shall be operation-specific.

5.1092 INTEGRATION AND API RISK ANALYSIS
Risk 1 — Controllers Contain the Whole Application
Problem
CONTROLLER   │   ├── VALIDATION   ├── BUSINESS RULES   ├── SQL   ├── SMS   ├── EMAIL   └── AUDIT
Impact
The application becomes difficult to test and maintain.
Mitigation
Use application and domain boundaries.

Risk 2 — React Directly Connects to PostgreSQL
Problem
REACT  │  ▼POSTGRESQL
Impact
DATABASE CREDENTIAL EXPOSUREAUTHORIZATION BYPASSBUSINESS RULE BYPASSDATABASE ATTACK SURFACE
Mitigation
All approved frontend business operations shall pass through the backend API.

Risk 3 — Database Entity Returned Directly
Problem
PATIENT DATABASE ENTITY          │          ▼JSON RESPONSE
Impact
New database fields may accidentally become externally visible.
Mitigation
Use explicit API response contracts.

Risk 4 — API Trusts React Validation
Problem
React validates:
AMOUNT > 0
Attacker sends direct API request:
AMOUNT = -100000
Impact
Invalid data may enter the system.
Mitigation
Backend validation shall be authoritative.

Risk 5 — Every Error Returns Stack Trace
Problem
API response contains:
NpgsqlExceptionDATABASE HOSTTABLE NAMEFILE PATHSOURCE CODE LINE
Impact
Internal architecture information is exposed.
Mitigation
Use standardized safe API errors.

Risk 6 — No API Version Strategy
Problem
React V1 expects:
patientName
Backend changes it to:
legalFullName
Impact
Production frontend fails.
Mitigation
Govern API contract changes.

Risk 7 — Unlimited Page Size
Problem
Client requests:
pageSize = 10,000,000
Impact
MEMORY PRESSUREDATABASE LOADAPI TIMEOUT
Mitigation
Enforce maximum page sizes.

Risk 8 — Client Sends Raw SQL Filter
Problem
filter = "status = 'ACTIVE' OR 1=1"
Impact
Security and query integrity risk.
Mitigation
Use approved filter contracts.

Risk 9 — No Idempotency for Payment Creation
Problem
Client retries after timeout.
Impact
Duplicate payment processing.
Mitigation
Use operation-specific idempotency.

Risk 10 — Every Timeout Is Retried
Problem
Provider processed payment but response was lost.
CuraSphere retries.
Impact
Duplicate financial action.
Mitigation
Apply operation-aware retry strategy.

Risk 11 — No Timeout
Problem
External provider never responds.
API waits indefinitely.
Impact
THREAD / CONNECTION EXHAUSTIONSLOW USER EXPERIENCESYSTEM DEGRADATION
Mitigation
Define integration timeouts.

Risk 12 — Retry Storm
Problem
External SMS provider fails.
10,000 messages retry immediately.
Impact
Provider and CuraSphere receive additional load.
Mitigation
Use controlled retry delays and attempt limits.

Risk 13 — Webhook Trusts Payload
Problem
Anyone sends:
payment.completed
Impact
Fake payment events may be processed.
Mitigation
Authenticate and validate webhook sources.

Risk 14 — Webhook Replay
Problem
A valid payment webhook is captured and sent 100 times.
Impact
Repeated business processing.
Mitigation
Use event deduplication and replay controls.

Risk 15 — Webhook Controller Updates Financial Tables Directly
Problem
WEBHOOK   │   ▼UPDATE invoicesSET paid = true
Impact
Billing business rules are bypassed.
Mitigation
Route validated events to Billing application services.

Risk 16 — Failed Messages Disappear
Problem
SMS delivery fails after retries.
Message is deleted.
Impact
Operations cannot investigate or reprocess it.
Mitigation
Maintain a failed-message boundary.

Risk 17 — External Model Becomes Domain Model
Problem
Payment provider DTO is used throughout Billing.
Impact
Changing payment provider changes the Billing domain.
Mitigation
Use mapping and adapter layers.

Risk 18 — External Patient ID Replaces CuraSphere ID
Problem
Patient ID:
EXT-99201
comes from Hospital A.
Hospital B also uses:
EXT-99201
Impact
Identifier collision.
Mitigation
Maintain system-specific external identifier mappings.

Risk 19 — Mapping Conflict Is Automatically Overwritten
Problem
One external patient identifier maps to two CuraSphere patients.
Impact
Clinical data may attach to the wrong patient.
Mitigation
Reject and investigate mapping conflicts.

Risk 20 — API Key Stored in Integration Table
Problem
integrations├── name├── endpoint└── api_key
Administrators can query the table.
Impact
Credential exposure.
Mitigation
Use secret management boundaries.

Risk 21 — Authorization Header Logged
Problem
Logs contain:
Authorization: Bearer eyJ...
Impact
Session or token exposure.
Mitigation
Redact sensitive headers.

Risk 22 — Business Module Uses SMS SDK Directly
Problem
APPOINTMENT SERVICE        │        ▼TWILIO SDK
Provider changes.
Impact
Appointment code requires modification.
Mitigation
Use notification and integration abstractions.

Risk 23 — FHIR Used as Internal Database Design
Problem
Every PostgreSQL table directly copies FHIR resource JSON.
Impact
Internal domain behavior becomes tightly coupled to an external interoperability model.
Mitigation
Use a FHIR mapping boundary.

Risk 24 — HL7 Message Automatically Updates Clinical State
Problem
External message arrives.
CuraSphere directly marks:
LAB RESULT VERIFIED
Impact
Clinical verification rules may be bypassed.
Mitigation
Route external information through the responsible clinical domain.

Risk 25 — DICOM Images Stored in Normal Transaction Tables
Problem
Large imaging binary data is inserted into ordinary radiology business rows.
Impact
Database growth and operational complexity increase.
Mitigation
Define dedicated medical imaging architecture.

Risk 26 — External Identity Means Internal Administrator
Problem
External identity provider returns:
role = admin
CuraSphere grants:
CURASPHERE SUPER ADMIN
Impact
Authorization governance is bypassed.
Mitigation
Control external-to-internal role mapping.

Risk 27 — Partner Uses Internal React API
Problem
An insurance provider receives access to internal UI endpoints.
Impact
Internal contracts and unnecessary data become externally exposed.
Mitigation
Define partner API boundaries.

Risk 28 — Complete Patient Record Sent to SMS Provider
Problem
SMS provider receives:
PATIENT HISTORYDIAGNOSISLAB RESULTSPHONE NUMBER
to send an appointment reminder.
Impact
Severe unnecessary data exposure.
Mitigation
Apply integration data minimization.

Risk 29 — One Integration Configuration for All Hospitals
Problem
Future hospitals use different providers.
Architecture contains:
SMS_PROVIDER = PROVIDER_A
globally.
Impact
Multi-hospital expansion requires redesign.
Mitigation
Preserve hospital-scoped integration resolution boundaries.

Risk 30 — Microservices Introduced Only Because Integrations Exist
Problem
Development team creates:
SMS MICROSERVICEEMAIL MICROSERVICEPAYMENT MICROSERVICEFHIR MICROSERVICEWEBHOOK MICROSERVICE
during the first RAD iteration.
Impact
DEPLOYMENT COMPLEXITYDISTRIBUTED DEBUGGINGNETWORK FAILURE MODESDEVOPS OVERHEAD
Mitigation
Start with clear modular boundaries and extract services only when architecture evidence requires it.
