5.158 MODULE PURPOSE
The Laboratory Management System shall manage the operational and clinical workflow associated with laboratory test orders, specimen collection, specimen accessioning, laboratory processing, result entry, technical or clinical verification, critical result handling, final laboratory reporting, and authorized result availability to the Electronic Medical Record.
The Laboratory module shall support the following high-level workflow:
CLINICAL ENCOUNTER        │        ▼LABORATORY ORDER        │        ▼TEST REQUEST        │        ▼SPECIMEN REQUIREMENT        │        ▼SPECIMEN COLLECTION        │        ▼SPECIMEN IDENTIFICATION        │        ▼LAB ACCESSION        │        ▼SPECIMEN RECEIPT        │        ▼SPECIMEN ACCEPTANCE / REJECTION        │        ▼LABORATORY PROCESSING        │        ▼RESULT ENTRY / INSTRUMENT RESULT        │        ▼RESULT REVIEW        │        ▼RESULT VERIFICATION        │        ├── CRITICAL RESULT WORKFLOW        │        ▼FINAL LABORATORY REPORT        │        ▼EMR AVAILABILITY
The Laboratory module shall provide traceability from the original clinical order to the finalized laboratory result.
Conceptually:
WHO ORDERED THE TEST?        │        ▼FOR WHICH PATIENT?        │        ▼DURING WHICH CLINICAL CONTEXT?        │        ▼WHAT TEST WAS REQUESTED?        │        ▼WHAT SPECIMEN WAS REQUIRED?        │        ▼WHAT SPECIMEN WAS COLLECTED?        │        ▼WHO COLLECTED IT?        │        ▼WHEN WAS IT RECEIVED?        │        ▼WAS IT ACCEPTED?        │        ▼WHAT RESULT WAS PRODUCED?        │        ▼WHO VERIFIED THE RESULT?        │        ▼WHEN DID IT BECOME FINAL?
This traceability is a fundamental laboratory requirement.

5.159 LABORATORY DOMAIN BOUNDARY
The Laboratory module shall manage laboratory operational workflow.
It shall not own the complete outpatient consultation.
The domain relationship is:
OPD / CLINICAL ENCOUNTER          │          ▼     LAB ORDER          │          ▼         LAB          │          ├── Test Catalog          ├── Specimen Requirements          ├── Collection          ├── Accession          ├── Processing          ├── Result Entry          ├── Verification          └── Laboratory Report          │          ▼         EMR
The responsibilities shall conceptually be divided as follows:
OPDDoctor decides:"Patient requires a CBC."
LABLaboratory manages:"How is the CBC specimen collected,received, processed, resulted,verified, and reported?"
EMRClinical record provides:"Authorized access to the finalizedCBC result in the patient'slongitudinal record."
The Laboratory module shall not be designed as a simple:
test_nameresult
table.
A real laboratory workflow contains multiple operational and clinical states.

5.160 CRITICAL LABORATORY ARCHITECTURE CONCEPT
CuraSphere shall distinguish the following concepts:
LAB ORDER
ORDERED TEST
SPECIMEN
ACCESSION
TEST PROCESSING
RESULT
LABORATORY REPORT
These concepts shall not automatically be treated as identical.
Conceptually:
LAB ORDER    │    ▼WHY AND WHAT WAS REQUESTED?
ORDERED TEST    │    ▼WHICH LABORATORY TEST?
SPECIMEN    │    ▼WHAT BIOLOGICAL MATERIALWAS COLLECTED?
ACCESSION    │    ▼HOW DID THE LAB RECEIVEAND TRACK THE WORK?
RESULT    │    ▼WHAT OBSERVATION OR VALUEWAS PRODUCED?
LABORATORY REPORT    │    ▼WHAT VERIFIED CLINICALLAB INFORMATION WAS RELEASED?
Example:
LAB ORDERORD-LAB-1001        │        ├── Complete Blood Count        ├── Blood Glucose        └── Liver Function Test
The order contains three requested tests.
The tests may not necessarily have identical specimen or processing requirements.
Another example:
COMPLETE BLOOD COUNT        │        ▼EDTA BLOOD SPECIMEN
URINE ROUTINE EXAMINATION        │        ▼URINE SPECIMEN
Therefore:
LAB ORDER = SPECIMEN
is an incorrect assumption.

5.163 LABORATORY TEST CATALOG MANAGEMENT
CS-LAB-FR-001 — Maintain Laboratory Test Catalog
Requirement Name
Maintain Laboratory Test Catalog
Description
The system shall maintain a controlled catalog of laboratory tests available within CuraSphere.
Priority
Must Have
Purpose
Doctors and clinical users shall order laboratory tests from an approved laboratory catalog rather than relying exclusively on unrestricted free-text test names.
Weak design:
Doctor types:"blood test""cbc""C.B.C""complete blood""complete blood count"
The system may interpret these as five unrelated values.
A controlled catalog provides:
TEST CODELAB-CBC
TEST NAMEComplete Blood Count
Conceptual Test Definition
LABORATORY TEST       │       ├── Test Code       ├── Test Name       ├── Department / Section       ├── Specimen Requirements       ├── Result Components       ├── Processing Information       ├── Active Status       └── Applicable Configuration

CS-LAB-BR-001
Each laboratory test definition shall have a unique internal identity.
CS-LAB-BR-002
Laboratory test codes shall be unique within their applicable coding scope.
CS-LAB-BR-003
Only active and orderable tests shall normally be available for new clinical orders.
CS-LAB-BR-004
Historical orders shall preserve their relationship to the applicable test definition.

5.168 SPECIMEN COLLECTION REQUIREMENT
CS-LAB-FR-016 — Identify Specimen Collection Requirement
Description
The system shall determine and present applicable specimen collection requirements for ordered laboratory tests.
Priority
Must Have
Example
ORDERED TESTSCBCBlood GlucoseUrine Routine Examination        │        ▼SPECIMEN REQUIREMENTSWhole Blood / EDTABlood / Configured ContainerUrine / Urine Container
Important Domain Problem
Consider:
TEST ARequires EDTA BloodTEST BRequires EDTA Blood
Can one specimen support both tests?
Possibly, depending on laboratory policy and specimen requirements.
Now consider:
TEST ARequires EDTA BloodTEST CRequires Urine
One specimen cannot represent both biological materials.
Therefore specimen planning requires explicit domain rules.
The SRS shall support specimen requirement configuration.
The exact specimen consolidation algorithm shall be defined during Laboratory Detailed Design.

5.211 LABORATORY MODULE RISK ANALYSIS
Risk 1 — Wrong Patient Specimen
Problem
A specimen collected from Patient A is associated with Patient B’s laboratory order.
Impact
Severe patient safety risk.
The wrong patient may receive:
an incorrect diagnosis;
inappropriate treatment;
unnecessary medication;
delayed treatment.
Mitigation
CuraSphere shall validate:
PATIENT   │   ▼LAB ORDER   │   ▼SPECIMEN
relationships through trusted backend logic.
Specimen identification and patient-context controls shall be treated as safety-critical requirements.

Risk 2 — Specimen Has No Unique Identity
Problem
The system only records:
sample_collected = true
Impact
The system cannot trace individual physical specimens.
Mitigation
Each tracked specimen shall receive a unique specimen identifier.

Risk 3 — Rejected Specimen Deleted
Problem
A laboratory user deletes the rejected specimen record.
Impact
The laboratory loses operational and quality traceability.
Mitigation
Use:
SPECIMEN   │   ▼REJECTED   │   ▼REASON   │   ▼RECOLLECTION
rather than uncontrolled deletion.

Risk 4 — One Result Column for Complex Tests
Problem
Database design:
lab_resultstest_nameresult
Impact
Multi-component tests become difficult to model.
Mitigation
Use:
TEST  │  ▼RESULT SET  │  ▼RESULT COMPONENTS

Risk 5 — Reference Range Hardcoded in React
Problem
if (hemoglobin < 12) {    status = "LOW";}
Impact
Clinical rules become duplicated and inconsistent.
Mitigation
Reference range evaluation shall use approved laboratory configuration and trusted backend logic.

Risk 6 — Abnormal and Critical Results Treated as Identical
Problem
Every abnormal result creates an emergency alert.
Impact
Alert fatigue and incorrect clinical workflow.
Mitigation
Distinguish:
ABNORMAL
from:
CRITICAL
using approved laboratory rules.

Risk 7 — Critical Result Only Displayed in Red
Problem
The UI shows:
CRITICAL
but no notification workflow exists.
Impact
Urgent laboratory information may not reach an appropriate clinical recipient.
Mitigation
Implement a formal critical result notification workflow.

Risk 8 — Final Result Silently Edited
Problem
A finalized result changes from:
6.8
to:
4.8
without correction history.
Impact
Clinical record integrity is lost.
Mitigation
Use controlled result correction and preserve the original result traceability.

Risk 9 — Draft Result Appears in EMR as Final
Problem
A technician enters an incomplete draft value.
The EMR immediately displays it as a final result.
Impact
Doctors may make clinical decisions using unverified information.
Mitigation
Result release shall respect result status and approved release rules.

Risk 10 — Instrument Result Matched by Patient Name
Problem
An instrument result is matched using:
"Ahmad Khan"
Impact
Duplicate names can cause incorrect patient result association.
Mitigation
Future instrument integration shall use validated laboratory identifiers and explicit mappings.

Risk 11 — One Date Field for Entire Laboratory Workflow
Problem
Database contains:
lab_date
Impact
The system cannot measure:
collection time;
transport time;
receipt time;
processing time;
verification time.
Mitigation
Record meaningful laboratory workflow timestamps.

Risk 12 — Recollection Reuses Old Specimen ID
Problem
Rejected specimen:
SPM-100
New physical specimen:
SPM-100
Impact
Physical specimen traceability becomes ambiguous.
Mitigation
Every newly collected physical specimen shall receive its own applicable specimen identity.
