5.1299 REPORTING DOMAIN BOUNDARY
The RPT/ANA module shall manage reporting, analytical calculation, KPI presentation, dashboard data, and approved analytical output.
It shall not own the underlying operational business transaction.
Example:
APPOINTMENT MODULE        │        ▼OWNS APPOINTMENTS
Reporting module:
RPT/ANA   │   ▼CALCULATES APPOINTMENT METRICS
Another example:
BILLING MODULE      │      ▼OWNS INVOICES AND PAYMENTS
Reporting module:
RPT/ANA   │   ▼CALCULATES REVENUE AND COLLECTION KPIs
Another example:
LABORATORY MODULE       │       ▼OWNS LAB ORDERS AND RESULTS
Reporting module:
RPT/ANA   │   ▼CALCULATES LAB TURNAROUND ANALYTICS
Critical Principle
OPERATIONAL MODULE        │        ▼OWNS BUSINESS FACT
RPT/ANA   │   ▼READS APPROVED FACTS   │   ▼CALCULATES ANALYTICAL INFORMATION
The reporting module shall not independently:
COMPLETE AN APPOINTMENTADMIT A PATIENTDISCHARGE A PATIENTVERIFY A LAB RESULTAPPROVE A RADIOLOGY REPORTDISPENSE MEDICATIONMARK AN INVOICE PAIDAPPROVE EMPLOYEE LEAVEGENERATE SALARY
because a dashboard value or report calculation changed.
Therefore:
ANALYTICAL RESULT       ≠OPERATIONAL COMMAND

5.1300 SOURCE OF TRUTH BOUNDARY
Every report and KPI shall use an approved source of truth.
Example:
KPITOTAL PAID REVENUE
Source:
BILLING / PAYMENT DOMAIN
The system shall not calculate paid revenue from:
REACT TABLE ROWS
or:
BROWSER LOCAL STORAGE
Conceptually:
SOURCE DOMAIN     │     ▼APPROVED DATA     │     ▼REPORTING LOGIC     │     ▼KPI / REPORT
Critical Principle
DISPLAYED DATA      ≠SOURCE OF TRUTH
Example:
A React page currently displays 25 invoices because:
PAGE SIZE = 25
The frontend shall not calculate:
TOTAL INVOICES = 25
unless the server explicitly states that the total count is 25.

5.1301 REACT ANALYTICS BOUNDARY
The React application shall present analytical information received from approved APIs.
Incorrect architecture:
REACT  │  ▼DOWNLOAD 500,000 APPOINTMENTS  │  ▼JavaScript Array.filter()  │  ▼COUNT COMPLETED APPOINTMENTS  │  ▼CALCULATE KPI
Preferred architecture:
REACT  │  ▼ANALYTICS API  │  ▼AUTHORIZATION  │  ▼REPORTING SERVICE  │  ▼SERVER-SIDE QUERY / AGGREGATION  │  ▼KPI RESULT  │  ▼REACT PRESENTATION
The React application may perform approved presentation calculations such as:
CHART LABEL FORMATTINGDATE DISPLAY FORMATTINGPERCENTAGE DISPLAY FORMATTINGVISUAL SORTING OF ALREADY APPROVED SMALL DATASETS
It shall not independently redefine hospital KPI business logic.
Therefore:
REACT   │   ▼PRESENTATION
and:
ASP.NET CORE / REPORTING DOMAIN               │               ▼AUTHORITATIVE KPI CALCULATION

5.1304 REGISTER REPORT DEFINITION
CS-RPT-FR-001 — Register Report Definition
The system shall allow authorized report administrators to register approved report definitions.
A report definition may include:
REPORT NAMEREPORT CATEGORYREPORT DESCRIPTIONREPORT OWNERSOURCE DOMAINPARAMETERSSUPPORTED FILTERSSUPPORTED SORTINGSUPPORTED EXPORTSSENSITIVITY CLASSIFICATION
Conceptually:
REPORT DEFINITION       │       ▼DATA SOURCE       │       ▼PARAMETERS       │       ▼CALCULATION / QUERY POLICY       │       ▼OUTPUT POLICY
The report definition shall remain distinct from a report execution.
Therefore:
REPORT DEFINITION        ≠REPORT EXECUTION

5.1305 REPORT IDENTIFIER
CS-RPT-FR-002 — Generate Report Identifier
The system shall generate a unique report definition identifier.
Example:
RPT-000128
The identifier shall remain stable across normal report configuration changes.
Example:
RPT-000128MONTHLY REVENUE SUMMARY
The display name may change according to approved configuration.
The identifier shall remain the stable system reference.

5.1317 SERVER-SIDE REPORT CALCULATION

The system shall perform authoritative report calculations through approved server-side reporting logic.
Incorrect:
REACTfetch("/appointments")      │      ▼appointments.filter(...)      │      ▼CALCULATE HOSPITAL KPI
Preferred:
REACT  │  ▼GET APPROVED ANALYTICS  │  ▼ASP.NET CORE  │  ▼REPORTING SERVICE  │  ▼CALCULATE KPI
The server shall define calculation rules for authoritative metrics.

according to architecture and performance requirements.

5.1425 REPORTING AND ANALYTICS RISK ANALYSIS
Risk 1 — React Calculates Hospital KPIs
Problem
React downloads operational records and calculates:
REVENUEBED OCCUPANCYAPPOINTMENT COMPLETION RATE
Impact
Different screens may produce different KPI values.
Mitigation
Use authoritative server-side KPI calculation.

Risk 2 — Pagination Data Is Treated as Complete Data
Problem
React receives:
25 RECORDS
because:
PAGE SIZE = 25
and displays:
TOTAL PATIENTS = 25
Impact
Management decisions use incorrect information.
Mitigation
Return authoritative total and KPI values from the server.

Risk 3 — KPI Formula Exists Only in Developer Code
Problem
No approved business definition exists for:
BED OCCUPANCY RATE
Impact
Developers make independent assumptions.
Mitigation
Maintain governed KPI definitions and business owners.

Risk 4 — Same KPI Uses Different Formulas
Problem
Dashboard A calculates:
COMPLETED / ALL APPOINTMENTS
Dashboard B calculates:
COMPLETED / NON-CANCELLED APPOINTMENTS
Both display:
APPOINTMENT COMPLETION RATE
Impact
Users lose trust in CuraSphere analytics.
Mitigation
Use one approved KPI definition.

Risk 5 — Report ID Grants Access
Problem
User changes:
RPT-000101
to:
RPT-000102
and opens a payroll report.
Impact
Sensitive information exposure.
Mitigation
Authorize every report request.

Risk 6 — Hospital Filter Bypasses Scope
Problem
Manager belongs to Hospital A.
Client sends:
hospitalId = HOSPITAL_B
Impact
Cross-hospital data exposure.
Mitigation
Validate hospital scope server-side.

Risk 7 — Patient ID Is Trusted From React
Problem
Patient changes:
patientId = PAT-001
to:
patientId = PAT-002
Impact
Another patient’s analytics may be exposed.
Mitigation
Derive patient scope from authenticated identity.

Risk 8 — Dashboard Gives Everyone All KPIs
Problem
One dashboard API returns:
PATIENT DATAREVENUEPAYROLLSECURITY EVENTSCLINICAL ANALYTICS
to every user.
Impact
Role boundaries disappear.
Mitigation
Use role and scope-aware dashboards.

Risk 9 — KPI Access Grants Detail Access
Problem
A manager can view:
PATIENT COUNT = 5,000
and therefore the system allows access to all 5,000 patient records.
Impact
Summary access becomes record-level access.
Mitigation
Authorize drill-down separately.

Risk 10 — Report View Permission Grants Export Permission
Problem
A user can view a restricted report.
The same user exports:
500,000 PATIENT RECORDS
Impact
Large-scale data extraction becomes possible.
Mitigation
Separate report view and export permissions.

Risk 11 — Unlimited Export Size
Problem
User requests millions of rows.
Impact
Memory, CPU, database, and security risk increase.
Mitigation
Apply export-size limits and background export boundaries.

Risk 12 — Sensitive Export Is Not Recorded
Problem
A payroll or patient report is exported.
No access event exists.
Impact
Security investigation becomes difficult.
Mitigation
Record eligible sensitive exports.

Risk 13 — CSV Injection
Problem
Exported cell begins with spreadsheet formula syntax.
Impact
Opening the CSV may trigger unsafe spreadsheet behavior.
Mitigation
Evaluate CSV injection protection during Security Architecture.

Risk 14 — Every Dashboard Refresh Runs Huge Queries
Problem
Every widget independently scans large transactional tables.
Impact
PostgreSQL performance degrades.
Mitigation
Use query optimization and future caching, read models, or pre-aggregation where justified.

Risk 15 — Dashboard Polls Every Second
Problem
Hundreds of users continuously refresh expensive KPIs.
Impact
Application and database load increase.
Mitigation
Define dashboard freshness and refresh policies.

Risk 16 — Real-Time Label on Delayed Data
Problem
Dashboard displays:
LIVE
but data is refreshed once daily.
Impact
Users make decisions based on incorrect freshness assumptions.
Mitigation
Expose data freshness and as-of time.

Risk 17 — 50-Year Interactive Report
Problem
User executes:
START: 1976END: 2026
on transactional data.
Impact
Long-running queries affect operational workloads.
Mitigation
Apply date-range limits and background analytical workflows.

Risk 18 — No Query Timeout Policy
Problem
A report query runs indefinitely.
Impact
Database and application resources remain occupied.
Mitigation
Define governed report timeout boundaries.

Risk 19 — Scheduled Reports Fail Silently
Problem
Monthly management report fails for six months.
No alert or execution history exists.
Impact
Management receives incomplete information.
Mitigation
Record scheduled executions and failures.

Risk 20 — Sensitive Report Sent as Open Email Attachment
Problem
A detailed patient report is automatically attached to ordinary email.
Impact
Sensitive information may leave controlled CuraSphere access boundaries.
Mitigation
Apply report delivery sensitivity policies.

Risk 21 — Background Job Stored Only in Memory
Problem
Long report is running.
ASP.NET Core application restarts.
Impact
The report execution disappears.
Mitigation
Use durable background processing boundaries for important jobs.

Risk 22 — Retry Every Failure Forever
Problem
Invalid report continuously retries.
Impact
Resources are wasted.
Mitigation
Classify failures and define retry eligibility.

Risk 23 — Reporting Admin Becomes Hospital Superuser
Problem
Report configuration permission grants access to:
ALL PATIENT RECORDSALL PAYROLL RECORDSALL FINANCIAL RECORDS
Impact
Technical administration becomes unrestricted business access.
Mitigation
Separate report configuration from report-content authorization.

Risk 24 — Reporting Queries Block Patient Care Workflows
Problem
A large analytical query consumes PostgreSQL resources.
At the same time:
PATIENT REGISTRATIONLAB RESULT ENTRYPAYMENT PROCESSING
become slow.
Impact
Operational hospital workflows are affected.
Mitigation
Protect transactional workloads through approved reporting architecture.

Risk 25 — Cache Leaks Hospital Data
Problem
Cache key:
dashboard-summary
stores Hospital A result.
Hospital B requests the same key.
Impact
Hospital A analytics are returned to Hospital B.
Mitigation
Cache policy shall include authorization and hospital scope.

Risk 26 — Stale Cache Is Presented as Current
Problem
Dashboard displays old values without freshness information.
Impact
Users assume the data is current.
Mitigation
Return as-of time and freshness classification.

Risk 27 — Materialized Data Has Unknown Refresh Time
Problem
Management sees a KPI.
No one knows when the underlying materialized data was refreshed.
Impact
The KPI cannot be interpreted correctly.
Mitigation
Track analytical data freshness.

Risk 28 — BI Tool Connects Directly With Full Production Access
Problem
A BI account receives unrestricted production database credentials.
Impact
Data exposure and operational database risk increase.
Mitigation
Use approved analytical data and access boundaries.

Risk 29 — Prediction Is Presented as Fact
Problem
Model predicts:
500 PATIENTS TOMORROW
UI displays:
500 PATIENTS WILL ARRIVE
Impact
Uncertainty is hidden.
Mitigation
Clearly classify predictive output.

Risk 30 — Machine Learning Model Version Is Unknown
Problem
A prediction exists.
The system cannot identify which model generated it.
Impact
Analytical reproducibility and investigation become difficult.
Mitigation
Preserve future model governance metadata.

Risk 31 — Anomaly Means Automatic Fraud Accusation
Problem
Anomaly model identifies unusual billing.
System marks employee:
FRAUDULENT
Impact
Analytical uncertainty becomes an unsupported accusation.
Mitigation
Treat anomaly detection as an investigation signal.

Risk 32 — Population Health Analytics Ignores Privacy
Problem
Patient data is reused for broad analytics without governance review.
Impact
Privacy and compliance risks increase.
Mitigation
Require privacy, data governance, and legal review.

Risk 33 — AI Recommendation Replaces Clinician
Problem
Analytical model recommends an action.
System automatically treats it as the final clinical decision.
Impact
Patient safety and clinical accountability may be affected.
Mitigation
Keep analytical recommendations distinct from final clinical decisions.

Risk 34 — Hospitals Compare Different KPI Definitions
Problem
Hospital A and Hospital B calculate occupancy differently.
Management ranks hospitals using the values.
Impact
The comparison is misleading.
Mitigation
Use governed comparable KPI definitions.

Risk 35 — Analytics Microservices Created Too Early
Problem
RAD team immediately creates:
REPORT MICROSERVICEKPI MICROSERVICEDASHBOARD MICROSERVICEEXPORT MICROSERVICESCHEDULER MICROSERVICEANALYTICS MICROSERVICE
Impact
NETWORK COMPLEXITYDEPLOYMENT COMPLEXITYDATA SYNCHRONIZATION PROBLEMSDISTRIBUTED FAILURE MODESDEVOPS OVERHEAD
Mitigation
Begin with a well-isolated modular reporting and analytics domain.
Extract independent analytical services only when scale and architecture evidence require them.
