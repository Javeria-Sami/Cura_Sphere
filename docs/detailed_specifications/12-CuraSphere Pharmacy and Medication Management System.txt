5.273 MODULE PURPOSE
The Pharmacy and Medication Management System shall manage the operational workflow associated with medication catalog management, medication ordering, prescription processing, pharmacy verification, medication dispensing, pharmacy inventory, medication batches, expiry tracking, stock movements, medication returns, dispensing cancellation, and authorized medication history availability.
The Pharmacy module shall support the following high-level workflow:
CLINICAL ENCOUNTER        │        ▼MEDICATION ORDER        │        ▼ORDER VALIDATION        │        ▼PRESCRIPTION        │        ▼PHARMACY WORK QUEUE        │        ▼PHARMACY VERIFICATION        │        ├── CLARIFICATION REQUIRED        │        ├── REJECTED / CANCELLED        │        ▼READY FOR DISPENSING        │        ▼STOCK AVAILABILITY CHECK        │        ▼BATCH SELECTION        │        ▼MEDICATION DISPENSING        │        ▼STOCK MOVEMENT        │        ▼DISPENSING COMPLETION        │        ▼PATIENT MEDICATION HISTORY        │        ▼EMR
The module shall provide traceability from the original clinical medication request to the actual medication quantity dispensed.
Conceptually:
WHO ORDERED THE MEDICATION?        │        ▼FOR WHICH PATIENT?        │        ▼DURING WHICH ENCOUNTER?        │        ▼WHICH MEDICATION WAS ORDERED?        │        ▼WHAT DOSE WAS ORDERED?        │        ▼WHAT ROUTE WAS ORDERED?        │        ▼WHAT FREQUENCY WAS ORDERED?        │        ▼FOR WHAT DURATION?        │        ▼WHO VERIFIED THE PRESCRIPTION?        │        ▼WHICH MEDICATION PRODUCT WAS DISPENSED?        │        ▼FROM WHICH INVENTORY BATCH?        │        ▼WHAT QUANTITY WAS DISPENSED?        │        ▼WHO DISPENSED IT?        │        ▼WHEN WAS IT DISPENSED?
This traceability shall be considered a fundamental pharmacy requirement.

5.274 PHARMACY DOMAIN BOUNDARY
The Pharmacy module shall manage pharmacy operational workflow and medication dispensing information.
It shall not own the complete clinical encounter.
The conceptual relationship is:
OPD / IPD / EMERGENCY          │          ▼    MEDICATION ORDER          │          ▼       PHARMACY          │          ├── Medication Catalog          ├── Prescription Queue          ├── Pharmacy Verification          ├── Dispensing          ├── Pharmacy Inventory          ├── Medication Batches          ├── Expiry Management          ├── Stock Movements          └── Returns          │          ▼          EMR
Responsibilities shall conceptually be divided as follows:
CLINICAL MODULEDoctor decides:"The patient requiresthis medication underthis clinical order."
PHARMACY MODULEPharmacy manages:"Can the eligible medicationorder proceed through pharmacyverification and dispensing?"
INVENTORY DOMAINInventory answers:"What physical stock exists,in which batch, at whichlocation, and what movementchanged that stock?"
EMRClinical record provides:"What eligible medicationinformation belongs to thepatient's longitudinal record?"
The Pharmacy module shall not be designed as:
patient_idmedicine_namequantity
A real medication workflow contains clinical, operational, and inventory states.

5.275 CRITICAL PHARMACY ARCHITECTURE CONCEPT
CuraSphere shall distinguish the following concepts:
MEDICATION DEFINITION
MEDICATION PRODUCT
MEDICATION ORDER
PRESCRIPTION
PHARMACY VERIFICATION
DISPENSING EVENT
MEDICATION BATCH
STOCK MOVEMENT
These concepts shall not automatically be treated as identical.
Conceptually:
MEDICATION DEFINITION        │        ▼WHAT CLINICAL MEDICATIONCONCEPT EXISTS?
MEDICATION PRODUCT        │        ▼WHAT DISPENSABLE PRODUCTIS AVAILABLE?
MEDICATION ORDER        │        ▼WHAT DID THE AUTHORIZEDCLINICIAN ORDER?
PRESCRIPTION        │        ▼WHAT MEDICATION INSTRUCTIONSARE PRESENTED FOR PHARMACYPROCESSING?
PHARMACY VERIFICATION        │        ▼WAS THE PRESCRIPTION REVIEWEDBY AN AUTHORIZED PHARMACY USER?
DISPENSING EVENT        │        ▼WHAT WAS ACTUALLY DISPENSED?
MEDICATION BATCH        │        ▼FROM WHICH PHYSICAL STOCKBATCH DID THE PRODUCT COME?
STOCK MOVEMENT        │        ▼WHY DID INVENTORY QUANTITYCHANGE?
Therefore:
MEDICATION     =PRESCRIPTION     =DISPENSING     =STOCK
is an incorrect architectural assumption.

5.276 CLINICAL MEDICATION VS DISPENSABLE PRODUCT
This distinction is fundamental to CuraSphere.
Example:
CLINICAL MEDICATIONParacetamol
A doctor may order:
ParacetamolDose:500 mgRoute:OralFrequency:Every 8 hours
The pharmacy may hold a specific product:
PRODUCTParacetamol 500 mg TabletDosage Form:TabletStrength:500 mgManufacturer:Configured ManufacturerPackage:100 Tablets
Another product may exist:
Paracetamol 120 mg / 5 mLDosage Form:Oral Suspension
Therefore:
MEDICATION CONCEPT        │        ▼CLINICAL ORDERING CONTEXT
is not always identical to:
MEDICATION PRODUCT        │        ▼PHYSICAL DISPENSABLE STOCK
The detailed terminology and medication coding architecture shall be defined during Clinical Data Architecture.

Requirement Name
Maintain Medication Catalog
Description
The system shall maintain a controlled catalog of medication definitions available within CuraSphere.
Priority
Must Have
Problem With Free Text
Weak design:
Doctor 1:Paracetamol
Doctor 2:Panadol
Doctor 3:PCM
Doctor 4:Paracetmol
The system may incorrectly create unrelated medication identities.
A controlled medication catalog provides:
MEDICATION CODEMED-PARACETAMOL
MEDICATION NAMEParacetamol

MEDICATION DEFINITION        │        ├── Medication Code        ├── Generic Name        ├── Medication Category        ├── Orderable Status        └── Active Status

CS-PHR-BR-002

CS-PHR-BR-003
Only eligible active medication definitions shall normally be available for new medication orders.
CS-PHR-BR-004

5.337 PHARMACY MODULE RISK ANALYSIS
Risk 1 — Medication Name Used as Complete Medication Model
Problem
The system stores:
medicine_name = "Paracetamol"
Impact
The system cannot reliably represent:
clinical medication identity;
strength;
dosage form;
dispensable product;
medication batch.
Mitigation
Separate medication definition, medication product, and medication batch concepts.

Risk 2 — Ordered Medication Treated as Dispensed Medication
Problem
The EMR shows:
Paracetamol — Dispensed
because a doctor ordered it.
Impact
Clinical users may incorrectly believe the patient received the medication.
Mitigation
Preserve medication order and dispensing states separately.

Risk 3 — Dose Stored as One Free-Text String
Problem
The system stores:
500mg oral 3 times for 5 days
as the only order representation.
Impact
The system cannot reliably reason about dose, route, frequency, or duration.
Mitigation
Use structured medication order concepts with permitted additional instructions.

Risk 4 — Medication Safety Rules Invented by Developers
Problem
Developers manually create drug interaction rules from internet searches or assumptions.
Impact
Incorrect clinical decision support may cause patient harm.
Mitigation
Use approved clinical governance and validated medication knowledge services.

Risk 5 — Product and Batch Treated as Same Record
Problem
The system stores:
Paracetamol 500 mgQuantity: 500Expiry: DEC 2026
Then a second batch arrives with a different expiry.
Impact
The data model cannot represent multiple physical batches.
Mitigation
Separate medication product and medication batch.

Risk 6 — Expired Batch Hidden Only in React
Problem
React removes expired batches from a dropdown.
A user manually calls the API with an expired batch ID.
Impact
Expired medication may be recorded as dispensed.
Mitigation
Backend expiry validation shall be authoritative.

Risk 7 — Stock Stored as a Manually Editable Number
Problem
A user changes:
quantity = 500
to:
quantity = 900
Impact
No movement explains the 400-unit increase.
Mitigation
Use controlled stock movement and adjustment workflows.

Risk 8 — Concurrent Dispensing Creates Negative Stock
Problem
Two pharmacy users dispense the same remaining inventory simultaneously.
Impact
The system records more medication as dispensed than physically available.
Mitigation
Use database transactions and appropriate concurrency control.

Risk 9 — Boolean Dispensed Field
Problem
The system stores:
dispensed = true
Impact
Partial dispensing cannot be represented.
Mitigation
Use dispensing events, quantities, and explicit workflow states.

Risk 10 — Batch Traceability Lost
Problem
The system records the product but not the batch used for dispensing.
Impact
The hospital cannot reliably determine which dispensing events used an affected batch.
Mitigation
Maintain dispensing-to-batch allocation traceability.

Risk 11 — Return Automatically Added to Saleable Stock
Problem
Every returned medication creates:
stock + quantity
Impact
Potentially unsuitable returned medication may become available for dispensing.
Mitigation
Use return disposition workflow.

Risk 12 — Dispensing Deleted During Cancellation
Problem
A completed dispensing row is deleted.
Impact
Medication and stock history become inconsistent.
Mitigation
Use controlled cancellation and stock reversal workflow.

Risk 13 — Stock Update and Dispensing Save Are Separate
Problem
Dispensing succeeds but stock update fails.
Impact
Inventory is incorrect.
Mitigation
Use appropriate transactional consistency boundaries.

Risk 14 — React Controls Pharmacy Authorization
Problem
Frontend code:
if (user.role === "Pharmacist") {    showVerifyButton();}
is treated as security.
Impact
API requests may bypass the interface.
Mitigation
ASP.NET Core authorization shall enforce pharmacy permissions.

Risk 15 — Drug Database Vendor Embedded in Core Domain
Problem
Every medication entity directly depends on one vendor’s API and identifier model.
Impact
Vendor replacement becomes expensive and risky.
Mitigation
Use medication terminology and safety integration contracts.
