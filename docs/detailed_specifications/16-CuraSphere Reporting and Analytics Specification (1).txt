5.595 REPORTING DOMAIN BOUNDARY
The RPT/ANA module shall provide reporting, analytical projections, metrics, KPIs, dashboards, and authorized decision-support views.
It shall not become the authoritative owner of operational transactions.
Conceptually:
PATIENT MODULE      │      ▼OWNS PATIENT TRANSACTIONS
BILLING MODULE      │      ▼OWNS BILLING TRANSACTIONS
INVENTORY MODULE      │      ▼OWNS INVENTORY TRANSACTIONS
HR MODULE      │      ▼OWNS WORKFORCE TRANSACTIONS
The Reporting module:
OPERATIONAL DATA      │      ▼AUTHORIZED REPORTING PROJECTION      │      ▼REPORT / DASHBOARD
Therefore:
REPORT   ≠SOURCE TRANSACTION
and:
DASHBOARD   ≠OPERATIONAL DATABASE OWNER
Example:
The Billing module answers:
What is the authoritative status of invoice INV-000421?
The Reporting module answers:
What is the total invoiced amount for the selected reporting period?
The Inventory module answers:
What stock movement changed the balance of item MED-421?
The Reporting module answers:
Which items currently meet the approved low-stock reporting condition?

5.596 CRITICAL REPORTING ARCHITECTURE CONCEPT
CuraSphere shall distinguish:
SOURCE TRANSACTION
REPORTING READ MODEL
METRIC
KPI
DASHBOARD
REPORT DEFINITION
REPORT EXECUTION
REPORT EXPORT
REPORTING SNAPSHOT
These concepts shall not be treated as one object.
Weak architecture:
dashboardControllerSELECT *FROM patientsJOIN appointmentsJOIN admissionsJOIN invoicesJOIN paymentsJOIN inventoryJOIN employeesJOIN attendance
for every dashboard request.
This approach may create:
SLOW QUERIESDUPLICATE COUNTSINCORRECT AGGREGATIONDATABASE LOADTIGHT COUPLINGDIFFICULT TESTINGUNSTABLE DASHBOARDS
A stronger conceptual model is:
OPERATIONAL MODULES        │        ▼REPORTING PROJECTION        │        ▼READ MODEL        │        ▼METRIC CALCULATION        │        ▼DASHBOARD QUERY        │        ▼REACT VISUALIZATION

5.607 AUTHORIZED DASHBOARD DRILL-DOWN
CS-RPT-FR-009 — Provide Authorized Dashboard Drill-Down
Priority
Should Have
The system should allow authorized users to drill down from an aggregate indicator into an eligible supporting view.
Example:
LOW STOCK ITEMS12
User selects the card:
12 │ ▼LOW STOCK REPORT │ ▼AUTHORIZED ITEM LIST
Critical Security Principle
Aggregate access does not automatically mean row-level access.
Example:
A manager may be authorized to see:
TOTAL PATIENTS421
but may not automatically be authorized to see:
421 PATIENT MEDICAL RECORDS
Therefore:
AGGREGATE PERMISSION        ≠RECORD DETAIL PERMISSION

5.696 REPORTING AND ANALYTICS RISK ANALYSIS
Risk 1 — Dashboard Queries Every Operational Table
Problem
Each dashboard request performs large joins across the hospital database.
Impact
SLOW DASHBOARDHIGH DATABASE LOADQUERY TIMEOUTSOPERATIONAL PERFORMANCE IMPACT
Mitigation
Use approved reporting projections and read models.

Risk 2 — Same KPI Has Different Definitions
Problem
Finance dashboard says:
REVENUE = PAYMENTS RECEIVED
Management report says:
REVENUE = INVOICED AMOUNT
Impact
Management loses trust in the system.
Mitigation
Maintain approved metric and KPI definitions.

Risk 3 — React Calculates Important KPIs
Problem
const completionRate =  completed / total * 100;
is the only authoritative calculation.
Impact
Different clients may calculate different values.
Mitigation
Perform authoritative metric calculation in ASP.NET Core reporting logic.

Risk 4 — Dashboard Shows Stale Data as Current
Problem
Reporting refresh failed at 08:00.
Dashboard at 15:00 shows:
CURRENT PATIENTS421
with no freshness warning.
Impact
Management may make decisions using outdated data.
Mitigation
Display data freshness and refresh failure context.

Risk 5 — Aggregate Access Exposes Patient Details
Problem
A manager can see patient statistics.
Drill-down opens full patient medical records.
Impact
Unauthorized clinical data exposure.
Mitigation
Separate aggregate permission from record-detail permission.

Risk 6 — Department Filter Is UI-Only
Problem
React only displays Cardiology.
User changes:
departmentId=2
to:
departmentId=8
Impact
Unauthorized departmental data exposure.
Mitigation
Enforce data scope in ASP.NET Core.

Risk 7 — Reports Allow Raw SQL
Problem
Ordinary reporting users type SQL.
Impact
DATA EXPOSUREDATABASE DAMAGE RISKPERFORMANCE RISKSECURITY BYPASS
Mitigation
Use controlled report definitions and approved query architecture.

Risk 8 — Doctor Performance Becomes Clinical Judgment
Problem
Doctor with fewer appointments is labeled:
POOR PERFORMER
Impact
Misleading and unfair evaluation.
Mitigation
Clearly distinguish operational indicators from clinical quality assessment.

Risk 9 — Bed Occupancy Denominator Is Wrong
Problem
Out-of-service beds are included in the denominator.
Impact
Occupancy percentage becomes misleading.
Mitigation
Define eligible operational bed criteria.

Risk 10 — Appointment Is Counted as OPD Encounter
Problem
Every appointment is counted as a clinical visit.
Impact
OPD statistics are inflated.
Mitigation
Use authoritative OPD encounter data.

Risk 11 — Prescription Is Counted as Dispensing
Problem
Prescription creation is treated as medicine issue.
Impact
Pharmacy reports are inaccurate.
Mitigation
Use authoritative dispensing events.

Risk 12 — Failed Payment Is Counted as Payment
Problem
Payment attempts are aggregated.
Impact
Financial reporting is overstated.
Mitigation
Use approved successful payment states.

Risk 13 — Current Recalculation Replaces Historical Report
Problem
July report changes after late data corrections.
Management cannot determine what the original July report showed.
Impact
Historical reporting traceability is lost.
Mitigation
Support approved reporting snapshots.

Risk 14 — Export Permission Equals View Permission
Problem
A user can view a summary card.
The same user exports 100,000 detailed rows.
Impact
Sensitive data extraction risk.
Mitigation
Separate view and export authorization.

Risk 15 — Reporting Query Blocks Hospital Operations
Problem
A large yearly report consumes PostgreSQL resources.
Patient registration and billing become slow.
Impact
Reporting affects patient care operations.
Mitigation
Use performance limits, read models, query optimization, and asynchronous execution where appropriate.

Risk 16 — Duplicate Counts Across Joins
Problem
One patient has:
3 APPOINTMENTS4 PAYMENTS
A direct join creates:
12 ROWS
The dashboard counts:
12 PATIENTS
Impact
Incorrect statistics.
Mitigation
Use domain-aware aggregation and reporting projections.

Risk 17 — Undefined Turnaround Time
Problem
One report calculates:
ORDER → RESULT
Another calculates:
SPECIMEN → RESULT
Both are labeled:
LAB TURNAROUND TIME
Impact
Metrics cannot be compared.
Mitigation
Define source event and end event for each metric.

Risk 18 — Sensitive Small-Group Analytics
Problem
A demographic report filters to a very small patient group.
Impact
Individuals may become identifiable.
Mitigation
Apply privacy, data minimization, and approved aggregation controls.

Risk 19 — Reporting Administrator Has All Data
Problem
Technical report configuration role automatically receives all patient and financial information.
Impact
Excessive privilege.
Mitigation
Separate report administration permission from report data access.

Risk 20 — AI Forecast Is Treated as Medical Advice
Problem
Future analytics predicts a pattern.
The system presents it as a diagnosis.
Impact
Clinical safety risk.
Mitigation
Maintain a strict predictive analytics and clinical decision boundary.
