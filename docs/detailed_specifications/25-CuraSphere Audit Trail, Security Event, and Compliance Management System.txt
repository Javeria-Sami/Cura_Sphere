5.1584 AUDIT DOMAIN BOUNDARY
The AUD/SEC module shall own centralized audit-event and security-event processing boundaries.
Source modules shall own their business facts.
Example:
PATIENT MODULE      │      ▼OWNS PATIENT DEMOGRAPHICS
Patient update:
PHONE NUMBER CHANGED
The Patient module shall:
VALIDATE CHANGEAUTHORIZE CHANGEUPDATE PATIENT RECORD
AUD/SEC shall:
RECORD ELIGIBLE CHANGE EVENTIDENTIFY ACTORIDENTIFY RESOURCEIDENTIFY ACTIONRECORD RESULTPRESERVE TRACEABILITY
Therefore:
AUDIT EVENT     ≠BUSINESS RECORD
AUD/SEC shall not become the source of truth for:
PATIENT DEMOGRAPHICSAPPOINTMENT STATUSCLINICAL DIAGNOSISLAB RESULTRADIOLOGY REPORTPRESCRIPTIONINVENTORY QUANTITYINVOICE BALANCEPAYMENT STATEEMPLOYEE SALARY
Critical Principle
SOURCE DOMAIN      │      ▼OWNS BUSINESS TRUTH
AUD/SEC   │   ▼OWNS ACTIVITY TRACEABILITY

5.1585 AUDIT LOG VERSUS APPLICATION LOG BOUNDARY
CuraSphere shall distinguish audit events from technical application logs.
Application log example:
DATABASE QUERY COMPLETED IN 42 MS
Audit event example:
USER USR-00128 VIEWED PATIENT PAT-00982
Security event example:
USER USR-00128 WAS DENIED ACCESSTO PATIENT PAT-00982
Therefore:
APPLICATION LOG      ≠AUDIT EVENT      ≠SECURITY EVENT
Application logs primarily support:
DEBUGGINGOPERATIONSPERFORMANCE DIAGNOSTICS
Audit events primarily support:
ACCOUNTABILITYTRACEABILITYCOMPLIANCE EVIDENCEACTIVITY INVESTIGATION
Security events primarily support:
THREAT DETECTIONSECURITY INVESTIGATIONABUSE INVESTIGATION
A single activity may create more than one event type where justified.

5.1586 REACT AUDIT BOUNDARY
React shall not be the authoritative creator of protected audit events.
Incorrect:
REACTauditLog.push({    userId,    action: "PATIENT_VIEWED"})
Preferred:
REACT  │  ▼ASP.NET CORE API  │  ▼AUTHENTICATION  │  ▼AUTHORIZATION  │  ▼DOMAIN ACTION  │  ▼SERVER-SIDE AUDIT EVENT
React may:
DISPLAY AUTHORIZED AUDIT DATASUBMIT AUDIT SEARCH FILTERSREQUEST AUDIT EXPORTDISPLAY SECURITY EVENT STATUSDISPLAY PATIENT ACCESS HISTORY WHERE AUTHORIZED
React shall not:
DEFINE AUTHORITATIVE ACTOR IDDEFINE AUTHORITATIVE HOSPITAL SCOPEDEFINE AUTHORITATIVE ACTION RESULTDELETE AUDIT HISTORYEDIT AUDIT HISTORYDIRECTLY INSERT PROTECTED AUDIT EVENTSSUPPRESS SERVER-SIDE AUDIT EVENTS
Critical Principle
CLIENT CLAIM     ≠AUDIT TRUTH

Example:
PATIENT_RECORD_VIEWED
Another:
PATIENT_PHONE_UPDATED
Another:
PAYMENT_RECORDED
Another:
ROLE_ASSIGNED
Conceptually:
ACTION  │  ▼AUDIT POLICY  │  ▼AUDIT ELIGIBLE?  │ ┌┴─┐ │  │YES NO │  │ ▼  ▼EVENT NO EVENT
The audit policy shall be centrally governed.

5.1753 AUDIT, SECURITY AND COMPLIANCE RISK ANALYSIS
Risk 1 — React Creates Authoritative Audit Events
Problem
The browser sends:
actorId = ADMINaction = SAFE_ACTION
Impact
The client can falsify audit evidence.
Mitigation
Create protected audit events from trusted server-side context.

Risk 2 — System Administrator Deletes Audit History
Problem
An administrator performs a privileged action and deletes the evidence.
Impact
Accountability and compliance evidence are destroyed.
Mitigation
Separate system administration from protected audit deletion authority.

Risk 3 — Audit Administrator Edits History
Problem
Audit administrator changes:
PAYMENT_REVERSED
to:
PAYMENT_VIEWED
Impact
Historical evidence becomes unreliable.
Mitigation
Use append-oriented persistence and no ordinary update workflow.

Risk 4 — No Patient Access Audit
Problem
Hundreds of employees view a patient record.
No access events exist.
Impact
Unauthorized access cannot be investigated.
Mitigation
Record eligible patient and clinical record access.

Risk 5 — Password Stored in Audit Event
Problem
Password change audit records old and new passwords.
Impact
Audit storage becomes a credential database.
Mitigation
Never store password values.

Risk 6 — Access Token Stored in Audit Metadata
Problem
JWT access token is logged.
Impact
Token theft from audit storage may permit account access.
Mitigation
Exclude raw authentication tokens.

Risk 7 — Provider Secret Stored in Configuration Audit
Problem
SMS configuration event records the API key.
Impact
Audit users can obtain provider credentials.
Mitigation
Audit the configuration action without storing the secret.

Risk 8 — Complete Clinical Note Copied Into Audit
Problem
Every note update copies the full note body into audit metadata.
Impact
AUD/SEC becomes a second clinical database with broader access.
Mitigation
Store event and resource references with governed field-level change boundaries.

Risk 9 — Every Database Field Is Audited Automatically
Problem
ORM serializes complete old and new entities.
Impact
Passwords, tokens, clinical data, and internal values may enter audit storage.
Mitigation
Use an explicit audit matrix and sensitive-data policy.

Risk 10 — No Role Assignment Audit
Problem
A user receives administrator privileges.
No event exists.
Impact
Privilege escalation cannot be traced.
Mitigation
Audit role and permission changes.

Risk 11 — Privileged Users Have Less Audit
Problem
Administrator actions are excluded because administrators are trusted.
Impact
The highest-risk actions have the weakest evidence.
Mitigation
Apply stronger audit requirements to privileged activity.

Risk 12 — Audit Search Is Universal
Problem
Every manager can search every audit event.
Impact
Clinical, payroll, financial, and security information is exposed.
Mitigation
Apply audit permission and record scope.

Risk 13 — Hospital A Auditor Reads Hospital B Events
Problem
Client changes hospital ID.
Impact
Cross-hospital audit information is exposed.
Mitigation
Derive organizational scope server-side.

Risk 14 — Patient Changes Patient ID in Access History Request
Problem
Patient requests another patient’s access history.
Impact
Private audit information is exposed.
Mitigation
Derive patient scope from authenticated identity.

Risk 15 — Audit Export Is Not Audited
Problem
Compliance user exports one million audit events.
No evidence exists.
Impact
Sensitive audit extraction cannot be investigated.
Mitigation
Audit audit-data exports.

Risk 16 — View Permission Automatically Grants Export
Problem
A user who can view ten events can export ten million events.
Impact
Bulk data exposure risk increases.
Mitigation
Separate audit view and export permissions.

Risk 17 — Audit Table Has Normal UPDATE Permission
Problem
Application database role can update audit rows.
Impact
A software defect may rewrite history.
Mitigation
Use restricted database roles and append-oriented design.

Risk 18 — No Tamper Detection
Problem
A privileged infrastructure actor modifies audit rows.
Impact
Modification may remain invisible.
Mitigation
Evaluate integrity and tamper-evidence mechanisms.

Risk 19 — Blockchain Added Without Engineering Need
Problem
The team assumes audit means blockchain.
Impact
Complexity increases without solving application authorization and database security.
Mitigation
Evaluate practical append-only, privilege, hashing, archival, and backup controls first.

Risk 20 — Audit Storage Failure Is Silently Ignored
Problem
Payment reversal succeeds.
Audit insert fails.
Application continues.
Impact
A critical financial action has no required evidence.
Mitigation
Define critical synchronous audit boundaries.

Risk 21 — Every Read Waits on a Remote Audit Service
Problem
Patient screen cannot load because remote audit service is slow.
Impact
Clinical workflows may become unavailable.
Mitigation
Use durable asynchronous boundaries for eligible events.

Risk 22 — Asynchronous Audit Is In Memory
Problem
Audit event waits in application memory.
The server restarts.
Impact
Required audit evidence is lost.
Mitigation
Use durable audit processing.

Risk 23 — Duplicate Delivery Creates False Duplicate Actions
Problem
One payment event is processed twice by an audit consumer.
Impact
History appears to show two payment actions.
Mitigation
Use event idempotency boundaries.

Risk 24 — Legitimate Repeated Actions Are Deduplicated
Problem
Doctor views the same patient twice.
System removes the second event as a duplicate.
Impact
Real activity history becomes incomplete.
Mitigation
Distinguish duplicate event delivery from repeated legitimate actions.

Risk 25 — Audit Search Loads Entire Table
Problem
React requests all audit records.
Impact
PostgreSQL and application memory are overloaded.
Mitigation
Use server-side filtering and pagination.

Risk 26 — Unindexed Audit Growth
Problem
Billions of events accumulate with poor query design.
Impact
Audit investigation becomes unusable.
Mitigation
Define indexing, partitioning, archival, and retention during Data Architecture.

Risk 27 — Audit Storage Fills Database Disk
Problem
Audit events grow continuously.
No capacity monitoring exists.
Impact
PostgreSQL storage exhaustion may affect the entire hospital system.
Mitigation
Monitor audit storage and define capacity thresholds.

Risk 28 — Security Event Equals Confirmed Attack
Problem
One anomaly automatically disables a doctor and reports compromise.
Impact
Legitimate clinical work may be disrupted.
Mitigation
Separate anomaly signals from confirmed findings.

Risk 29 — Security Events Are Never Acknowledged
Problem
Critical alerts remain open for days.
Impact
Security response is delayed.
Mitigation
Monitor unacknowledged high-severity events.

Risk 30 — Audit Logs Used as Distributed Traces
Problem
Every low-level technical span is retained as compliance audit evidence.
Impact
Storage grows uncontrollably and audit meaning becomes unclear.
Mitigation
Keep tracing and audit concepts distinct.

Risk 31 — Distributed Traces Used as Audit Trail
Problem
Sampled traces are treated as complete audit evidence.
Impact
Required actions may be missing.
Mitigation
Use explicit required audit events.

Risk 32 — Kafka Added Before Modular Architecture Exists
Problem
The RAD team introduces distributed event infrastructure on day one.
Impact
Deployment, debugging, and DevOps complexity increase.
Mitigation
Start with modular AUD/SEC boundaries and PostgreSQL-based durability where appropriate.

Risk 33 — Separate Audit Microservice on Day One
Problem
Every business transaction depends on a network call to an immature audit microservice.
Impact
Network failure becomes a hospital-wide workflow dependency.
Mitigation
Define domain and persistence boundaries first; extract services only when justified.

Risk 34 — SIEM Receives Full Patient Records
Problem
Complete clinical data is forwarded with every security event.
Impact
Sensitive patient data spreads into security tooling.
Mitigation
Forward approved security context and minimum required references.

Risk 35 — AI Has Unrestricted Audit Access
Problem
AI investigation system receives all patient, payroll, financial, and security audit data.
Impact
Data governance and privacy exposure increase.
Mitigation
Apply explicit scope, minimization, authorization, and governance to AI-assisted investigation.
