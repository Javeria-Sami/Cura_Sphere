5.1096 NOTIFICATION DOMAIN BOUNDARY
The NTF/COM module shall manage notification and communication processing.
It shall not own the business event that caused the notification.
Example:
APPOINTMENT MODULE        │        ▼OWNS APPOINTMENT
Notification module:
NTF/COM   │   ▼OWNS APPOINTMENT REMINDER DELIVERY
Therefore:
APPOINTMENT BUSINESS STATE             ≠NOTIFICATION DELIVERY STATE
Another example:
BILLING MODULE      │      ▼OWNS INVOICE
Notification module:
NTF/COM   │   ▼OWNS INVOICE REMINDER COMMUNICATION
Therefore:
INVOICE STATUS      ≠MESSAGE STATUS
Another example:
IAM / SECURITY      │      ▼OWNS PASSWORD SECURITY EVENT
Notification module:
NTF/COM   │   ▼DELIVERS SECURITY COMMUNICATION
Critical Principle
BUSINESS MODULE      │      ▼DECIDES WHY COMMUNICATION IS NEEDED
NOTIFICATION MODULE         │         ▼MANAGES HOW COMMUNICATION IS PREPARED,ROUTED, DELIVERED AND TRACKED
The Notification module shall not independently:
CANCEL APPOINTMENTSCHANGE DIAGNOSESAPPROVE LAB RESULTSDISPENSE MEDICINESMARK INVOICES PAIDREVERSE PAYMENTSAPPROVE LEAVECHANGE USER PERMISSIONS
because a notification was delivered, read, or acknowledged.

5.1097 NOTIFICATION VS INTEGRATION BOUNDARY
CuraSphere shall distinguish:
NOTIFICATION DOMAIN
from:
INTEGRATION DOMAIN
Notification domain responsibilities:
WHO RECEIVES?WHAT MESSAGE?WHICH TEMPLATE?WHICH CHANNEL?WHEN TO SEND?IS COMMUNICATION ALLOWED?IS THE MESSAGE MANDATORY?WHAT IS THE NOTIFICATION STATUS?
Integration domain responsibilities:
HOW TO CALL SMS PROVIDER?HOW TO CALL EMAIL PROVIDER?WHAT IS THE PROVIDER TIMEOUT?SHOULD THE PROVIDER REQUEST RETRY?HOW IS THE PROVIDER RESPONSE MAPPED?HOW ARE PROVIDER CREDENTIALS PROTECTED?
Conceptually:
BUSINESS MODULE       │       ▼NOTIFICATION MODULE       │       ▼CHANNEL DELIVERY REQUEST       │       ▼INTEGRATION MODULE       │       ▼PROVIDER ADAPTER       │       ▼EXTERNAL PROVIDER
Incorrect architecture:
APPOINTMENT CONTROLLER          │          ▼SMS PROVIDER SDK
Incorrect architecture:
BILLING SERVICE      │      ▼SMTP CODE
Preferred:
APPOINTMENT DOMAIN        │        ▼NOTIFICATION REQUEST        │        ▼NTF/COM        │        ▼SMS DELIVERY BOUNDARY        │        ▼INT/API        │        ▼SMS PROVIDER

5.1098 NOTIFICATION CONCEPT
A notification shall represent an approved communication item created for one or more eligible recipients.
Conceptually:
NOTIFICATION     │     ├── Notification ID     ├── Notification Type     ├── Source Module     ├── Source Event     ├── Source Reference     ├── Recipient     ├── Template Reference     ├── Template Version     ├── Priority     ├── Channel     ├── Scheduled Time     ├── Expiration Time     ├── Status     ├── Created Time     └── Correlation Reference
Example:
NOTIFICATION IDNTF-0004821TYPEAPPOINTMENT_REMINDERSOURCE MODULEAPPOINTMENTSOURCE REFERENCEAPT-000421RECIPIENTPAT-000108CHANNELSMSSTATUSDELIVERED
The notification shall preserve sufficient information to understand its processing history.

5.1099 COMMUNICATION CHANNEL CONCEPT
A communication channel shall represent an approved delivery mechanism.
Potential channels include:
IN_APPSMSEMAILPUSH
Initial CuraSphere support may prioritize:
IN_APPSMSEMAIL
Future support may include:
MOBILE PUSH
The SRS shall not assume that every notification supports every channel.
Example:
SYSTEM MAINTENANCE NOTICE          │          ├── IN_APP          └── EMAIL
Appointment reminder:
APPOINTMENT REMINDER          │          ├── SMS          ├── EMAIL          └── IN_APP
Security alert:
SECURITY ALERT      │      ├── EMAIL      └── IN_APP
The approved channel matrix shall be defined during Notification Detailed Design.

Example:
APPOINTMENT CONFIRMED         │         ▼CREATE NOTIFICATION REQUEST
Potential request information includes:
NOTIFICATION TYPESOURCE MODULESOURCE EVENTSOURCE REFERENCERECIPIENT REFERENCETEMPLATE CODETEMPLATE VARIABLESCHANNEL PREFERENCEPRIORITYSCHEDULED TIMEEXPIRATION TIMEIDEMPOTENCY REFERENCE
The request shall be validated before a notification is accepted.
Conceptually:
NOTIFICATION REQUEST         │         ▼VALIDATE         │     ┌───┴───┐     │       │   VALID   INVALID     │       │     ▼       ▼  CREATE    REJECT

PATIENTUSERSTAFF MEMBERROLE AUDIENCEDEPARTMENT AUDIENCEHOSPITAL AUDIENCE

PATIENTPAT-000108

5.1121 TEMPLATE CHANNEL

Each template shall be associated with an approved communication channel.
Example:

TEMPLATEAPPOINTMENT_REMINDER_EMAILCHANNELEMAIL

5.1122 TEMPLATE VARIABLES
CS-NTF-FR-021 — Define Template Variables
The system shall support approved template variables.
Example template:
Dear {{PatientName}},your appointment is scheduled for {{AppointmentDate}}at {{AppointmentTime}}.
Variables:
PatientNameAppointmentDateAppointmentTime
Template variables shall be explicitly defined.
The system shall not support unrestricted code execution inside templates.
Incorrect:
{{ ExecuteDatabaseQuery() }}
Incorrect:
{{ RunShellCommand() }}
Templates shall be content-rendering structures, not executable programs.

5.1123 TEMPLATE VARIABLE VALIDATION
CS-NTF-FR-022 — Validate Template Variables
The system shall validate required template variables before message rendering.
Example template requires:
PatientNameAppointmentDateAppointmentTime
Request provides:
PatientNameAppointmentDate
Missing:
AppointmentTime
Result:
TEMPLATE VARIABLE VALIDATION FAILURE
The system shall not silently send:
Dear Ali,your appointment is scheduled for 14 July at {{AppointmentTime}}.
unless an explicitly approved fallback rule exists.

5.1124 MESSAGE RENDERING
CS-NTF-FR-023 — Render Notification Message
The system shall render notification content using the approved template and validated variables.
Conceptually:
TEMPLATE   │   ▼VARIABLES   │   ▼RENDERING ENGINE   │   ▼RENDERED MESSAGE
Example:
TEMPLATEDear {{PatientName}}, your appointment is on {{AppointmentDate}}.
Variables:
PatientName = AliAppointmentDate = 15 July 2026
Result:
Dear Ali, your appointment is on 15 July 2026.
Rendered content shall follow channel restrictions.

5.1125 TEMPLATE VERSION PRESERVATION
CS-NTF-FR-024 — Preserve Template Version
The system shall preserve the template version associated with an eligible notification.
Example:
TEMPLATEAPPOINTMENT_REMINDER_SMSVERSION3
Notification created using Version 3.
Later, the administrator creates Version 4.
Historical notification:
NTF-0004821
shall remain traceable to:
VERSION 3
The system shall not falsely indicate that Version 4 was used.

5.1127 DEACTIVATE NOTIFICATION TEMPLATE

5.1189 NOTIFICATION AND COMMUNICATION RISK ANALYSIS
Risk 1 — Every Module Sends Its Own SMS
Problem
APPOINTMENT    │    ▼SMS SDK
BILLING   │   ▼SMS SDK
PHARMACY    │    ▼SMS SDK
Impact
Provider logic is duplicated across the software.
Mitigation
Use centralized Notification and Integration boundaries.

Risk 2 — Notification Module Owns Business State
Problem
SMS delivered.
Notification module changes:
APPOINTMENT = CONFIRMED
Impact
Communication delivery controls appointment business state.
Mitigation
The Appointment domain shall own appointment state.

Risk 3 — Appointment Creation Waits for SMS
Problem
CREATE APPOINTMENT        │        ▼WAIT FOR SMS PROVIDER        │        ▼SMS PROVIDER DOWN        │        ▼APPOINTMENT API FAILS
Impact
External provider failure damages core hospital workflow.
Mitigation
Use asynchronous notification delivery where appropriate.

Risk 4 — One Generic Message Field
Problem
notifications└── message
No source, template, recipient, or channel information exists.
Impact
Traceability and controlled communication become difficult.
Mitigation
Use a structured notification model.

Risk 5 — Template Is Edited In Place
Problem
Template Version 1 is used for 50,000 messages.
Administrator changes the same record.
Historical messages now appear to use the new text.
Impact
Historical communication traceability is inaccurate.
Mitigation
Preserve template versions.

Risk 6 — Missing Template Variables Are Ignored
Problem
Message:
Your appointment is at {{AppointmentTime}}.
Impact
Broken messages are sent to patients.
Mitigation
Validate required variables before rendering.

Risk 7 — Templates Execute Code
Problem
Administrator inserts executable logic into a template.
Impact
Potential application or infrastructure compromise.
Mitigation
Use restricted template rendering.

Risk 8 — Every Notification Goes to Every Channel
Problem
Appointment event generates:
SMSEMAILIN-APPPUSH
regardless of policy.
Impact
Communication spam and unnecessary provider cost.
Mitigation
Use notification-type and channel policies.

Risk 9 — Invalid Phone Number Is Retried Forever
Problem
INVALID MOBILE NUMBER
classified as temporary.
Impact
Infinite retry and provider cost.
Mitigation
Classify permanent recipient failures.

Risk 10 — Provider Timeout Causes Duplicate SMS
Problem
Provider accepts SMS.
Response is lost.
CuraSphere retries immediately.
Impact
Patient receives duplicate messages.
Mitigation
Use provider-aware retry and idempotency controls.

Risk 11 — Appointment Reminder Sent After Cancellation
Problem
Reminder was scheduled yesterday.
Appointment cancelled today.
Reminder worker sends:
Your appointment is tomorrow.
Impact
Patient receives incorrect information.
Mitigation
Revalidate source eligibility for time-sensitive reminders.

Risk 12 — Notification Cancellation Pretends to Recall SMS
Problem
Delivered SMS status is changed to:
CANCELLED
UI claims the patient no longer has the message.
Impact
Operational users receive false information.
Mitigation
Separate CuraSphere processing cancellation from external message recall capability.

Risk 13 — No Notification Expiration
Problem
An urgent workflow alert is delayed for three days.
The worker later sends it.
Impact
Obsolete communication creates confusion.
Mitigation
Support expiration.

Risk 14 — Duplicate Business Event Creates Duplicate Message
Problem
The same appointment event is processed five times.
Impact
Patient receives five reminders.
Mitigation
Use notification deduplication and idempotency.

Risk 15 — One Boolean sent
Problem
sent = true
Does this mean:
QUEUED?SENT TO PROVIDER?PROVIDER ACCEPTED?DELIVERED?READ?
Impact
Notification status is ambiguous.
Mitigation
Use explicit notification and channel status models.

Risk 16 — Read Means Acknowledged
Problem
A user opens a critical notice accidentally.
The system records:
ACKNOWLEDGED
Impact
The system falsely claims explicit acknowledgment.
Mitigation
Separate read and acknowledgment states.

Risk 17 — User Marks Another User’s Notification Read
Problem
API:
POST /notifications/{id}/read
does not verify recipient scope.
Impact
Notification integrity and privacy are violated.
Mitigation
Enforce recipient-scoped access.

Risk 18 — Full Clinical Result Sent by SMS
Problem
Sensitive diagnosis or laboratory details are placed in an SMS.
Impact
Sensitive medical information may be exposed.
Mitigation
Apply channel-specific clinical content restrictions.

Risk 19 — Complete Patient Record Sent to Notification Provider
Problem
SMS provider receives a complete patient object.
Impact
Unnecessary sensitive information is exposed.
Mitigation
Use minimum required delivery data.

Risk 20 — Notification Administrator Sees All Clinical Content
Problem
Template management permission grants access to all rendered patient messages.
Impact
Administrative privilege becomes clinical data privilege.
Mitigation
Separate template administration from sensitive message-content access.

Risk 21 — No Communication Preference
Problem
A patient disables optional email communication.
The system continues sending optional messages.
Impact
Poor communication governance.
Mitigation
Apply approved preferences.

Risk 22 — Mandatory Notification Ignores Security
Problem
A message is marked:
MANDATORY
The system sends complete clinical data through any available channel.
Impact
Sensitive information exposure.
Mitigation
Mandatory status shall not bypass content-security policies.

Risk 23 — Failover Moves Sensitive Data to SMS
Problem
Secure in-app notification fails.
System copies detailed clinical content into SMS.
Impact
Security policy is bypassed.
Mitigation
Channel failover shall re-evaluate content eligibility.

Risk 24 — Notification Queue Is In Application Memory
Problem
10,000 reminders are scheduled in server memory.
Application restarts.
Impact
All reminders disappear.
Mitigation
Use a durable scheduling or work-processing boundary.

Risk 25 — Failed Notification Silently Disappears
Problem
Delivery fails after maximum retries.
No failure record exists.
Impact
Hospital operations cannot investigate.
Mitigation
Maintain notification and delivery attempt history.

Risk 26 — Unlimited Notification History API
Problem
Client requests every notification ever created.
Impact
Database and application load increase.
Mitigation
Use pagination and approved filtering.

Risk 27 — Notification Logs Store Message Content
Problem
Application logs contain:
PATIENT NAMEDIAGNOSISLAB RESULTPHONE NUMBER
Impact
Sensitive information is copied into technical logs.
Mitigation
Use logging minimization and redaction.

Risk 28 — Campaign Communication Uses Transactional Consent Rules
Problem
Marketing message is treated as an appointment confirmation.
Impact
Communication governance is bypassed.
Mitigation
Separate transactional and campaign communication concepts.

Risk 29 — Global Reminder Policy for Every Hospital
Problem
REMINDER = 24 HOURS
is hardcoded globally.
Impact
Future hospitals cannot apply approved local policies.
Mitigation
Preserve hospital-specific notification configuration boundaries.

Risk 30 — Notification Microservice Created Too Early
Problem
The RAD team immediately creates:
NOTIFICATION MICROSERVICESMS MICROSERVICEEMAIL MICROSERVICETEMPLATE MICROSERVICE
Impact
DISTRIBUTED TRANSACTIONSDEPLOYMENT COMPLEXITYNETWORK FAILURE MODESDEBUGGING COMPLEXITYDEVOPS OVERHEAD
Mitigation
Begin with a well-isolated modular notification domain and extract services only when architectural evidence requires it.
