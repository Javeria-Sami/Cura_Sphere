5. FUNCTIONAL REQUIREMENTS
5.1 Introduction
Functional requirements define the specific behaviors and capabilities that CuraSphere shall provide.
A functional requirement answers:
What shall the system do?
Examples include:
authenticate a user;
register a patient;
schedule an appointment;
record a diagnosis;
create a prescription;
collect a laboratory sample;
generate an invoice;
record a payment.
Functional requirements shall form the primary implementation baseline for CuraSphere.
The engineering relationship is:
STAKEHOLDER REQUIREMENT          │          ▼FUNCTIONAL REQUIREMENT          │          ▼       USE CASE          │          ▼      USER STORY          │          ▼       UI FLOW          │          ▼     API OPERATION          │          ▼     DOMAIN LOGIC          │          ▼       DATA MODEL          │          ▼       TEST CASE

5.2 Functional Requirement Documentation Standard
Each detailed functional requirement shall use the following structure.
Requirement ID:Requirement Name:Module:Requirement Type:Description:Source:Primary Actor:Secondary Actors:Priority:Preconditions:Trigger:Main Requirement:Main Flow:Alternate Flow:Exception Flow:Business Rules:Inputs:Outputs:Postconditions:Security Considerations:Audit Requirements:Acceptance Criteria:Dependencies:Traceability:Status:
Not every field shall contain the same amount of detail.
The level of detail shall depend on the requirement’s complexity and risk.

5.3 Requirement Priority Classification
CuraSphere shall use the MoSCoW priority model.

5.4 Functional Requirement Quality Rules
A functional requirement should be:
necessary;
clear;
uniquely identified;
testable;
traceable;
implementation-neutral where appropriate;
consistent;
feasible;
sufficiently detailed.
A weak requirement is:
The login should be good.
This requirement is ambiguous and cannot be reliably tested.
A stronger requirement is:
The system shall allow an active user to submit valid authentication credentials and establish an authenticated application session after successful identity verification.
The second requirement can be analyzed and tested.

5.5 IAM — IDENTITY AND ACCESS MANAGEMENT
5.5.1 Module Purpose
The Identity and Access Management module shall manage digital user identities and control access to CuraSphere.
The IAM module provides the security entry point for protected CuraSphere functionality.
The module shall support:
user account management;
authentication;
authorization support;
role management;
permission management;
account lifecycle management;
password management;
account recovery;

5.6 USER ACCOUNT MANAGEMENT REQUIREMENTS
CS-IAM-FR-001 — Create User Account
Requirement Name
Create User Account
Module
IAM — Identity and Access Management
Requirement Type
Functional Requirement
Description
The system shall allow an authorized System Administrator to create a CuraSphere user account.
Source
CS-SAD-SR-001 — User Account Management
Primary Actor
System Administrator
Secondary Actors
IAM Module
Priority
Must Have
Preconditions
The System Administrator is authenticated.
The System Administrator has user creation permission.
Required account information is available.
Trigger
The System Administrator initiates the user account creation process.
Main Requirement
The system shall allow an authorized System Administrator to provide required user account information and create a new CuraSphere user account.
Main Flow
1. System Administrator opens user management.2. System Administrator selects Create User.3. CuraSphere presents the user creation interface.4. System Administrator provides required account information.5. CuraSphere validates the provided information.6. CuraSphere verifies applicable uniqueness rules.7. System Administrator confirms account creation.8. CuraSphere creates the user account.9. CuraSphere assigns the configured initial account status.10. CuraSphere records the administrative action.11. CuraSphere confirms successful account creation.
Alternate Flow A — Optional Employee Association
If the account belongs to an existing hospital employee:
Administrator searches employee          │          ▼Selects employee          │          ▼CuraSphere associates user accountwith approved employee reference
The IAM account and HR employee record shall remain logically separate.
Exception Flow A — Duplicate Account Identifier
If an account identifier required to be unique already exists:
The system shall reject account creation.
The system shall identify the conflicting field in an appropriate manner.
The system shall not create a duplicate account.
Exception Flow B — Invalid Required Information
If required information is missing or invalid:
The system shall reject the submission.
The system shall identify validation problems.
Valid entered information should be preserved where technically appropriate.
Business Rules
CS-IAM-BR-001
Each user account shall have a unique internal system identifier.
CS-IAM-BR-002
Account identifiers configured as unique shall not be duplicated.
CS-IAM-BR-003
Creating a user account shall not automatically provide unrestricted system access.
CS-IAM-BR-004
Role or permission assignment shall follow approved authorization workflows.
Inputs
Potential inputs include:
username or approved login identifier;
account display information;
employee reference where applicable;
initial account status;
approved role assignment information.
The exact account fields shall be finalized during data requirements specification.
Outputs
new user account;
unique user identifier;
account creation confirmation;
audit event.
Postconditions
A valid user account exists within the IAM domain.
Security Considerations
Only users with approved account creation permission shall perform this operation.
Audit Requirements
The system shall record:
acting user identity;
account creation action;
created account identifier;
event timestamp;
operation result.
Sensitive authentication secrets shall not be stored in audit logs.
Acceptance Criteria
AC-001
Given an authenticated administrator with account creation permission, when valid unique account information is submitted, then a new user account shall be created.
AC-002
Given duplicate unique account information, when account creation is submitted, then the system shall reject the duplicate.
AC-003
Given a user without account creation permission, when the user attempts the protected operation, then the operation shall be denied.
Dependencies
AUD — Audit Management
HR — Human Resource Management, where employee association is used
Traceability
CS-SAD-SR-001
Future Use Case: UC-IAM-001
Future Test Group: TG-IAM-USER
Status
Proposed

CS-IAM-FR-002 — Authenticate User
Requirement Name
Authenticate User
Description
The system shall allow an eligible CuraSphere user to authenticate using approved credentials.
Source
CS-SEC-SR-005 — Authentication Security
Primary Actor
Hospital User
Priority
Must Have
Preconditions
The user account exists.
The authentication service is available.
The user has access to the CuraSphere authentication interface.
Trigger
The user submits authentication credentials.
Main Requirement
The system shall validate submitted credentials and establish an authenticated user context only after successful authentication.
Main Flow
USER  │  ▼OPEN LOGIN  │  ▼ENTER CREDENTIALS  │  ▼SUBMIT  │  ▼VALIDATE REQUEST  │  ▼FIND ACCOUNT  │  ▼VERIFY ACCOUNT STATUS  │  ▼VERIFY CREDENTIAL  │  ▼AUTHENTICATION SUCCESS  │  ▼CREATE AUTHENTICATED CONTEXT  │  ▼LOAD AUTHORIZED APPLICATION
Business Rules
CS-IAM-BR-005
Authentication success shall require valid credentials.
CS-IAM-BR-006
An inactive account shall not establish a normal authenticated session.
CS-IAM-BR-007
A locked account shall be handled according to the account lock policy.
CS-IAM-BR-008
Authentication failure shall not expose sensitive account information.
Inputs
approved login identifier;
password or approved authentication credential.
Outputs
On success:
authenticated user context;
authentication/session information.
On failure:
controlled authentication failure response.
Postconditions
Successful authentication creates an authorized authentication context.
Failed authentication does not create an authenticated context.
Security Considerations
The system must not:
return the stored password;
log plaintext passwords;
expose credential secrets;
disclose unnecessary account existence information.
Audit Requirements
Authentication success shall be recorded as a security-relevant event.
Authentication failure shall be recorded according to the security logging policy.
Acceptance Criteria
AC-001
Given an active eligible account and valid credentials, when authentication is submitted, then the user shall be authenticated.
AC-002
Given invalid credentials, when authentication is submitted, then authentication shall fail.
AC-003
Given an inactive account, when otherwise valid credentials are submitted, then normal authentication shall not succeed.

CS-IAM-FR-003 — Reject Invalid Authentication
Description
The system shall reject authentication when submitted credentials cannot be successfully verified.
Priority
Must Have
Primary Actor
Hospital User
Trigger
Invalid authentication information is submitted.
Main Requirement
The system shall deny authentication and shall not establish an authenticated user context.
Security Rule
The failure response shall not unnecessarily reveal whether:
the username exists;
the password alone was incorrect;
sensitive account details exist.
An approved generic response may be used.
Example conceptual message:
Unable to authenticate with the provided credentials.
Acceptance Criteria
Given invalid authentication credentials, when authentication is attempted, then:
authentication shall fail;
no authenticated context shall be established;
the event shall be handled according to failed authentication rules.

CS-IAM-FR-013 — Remove Permission from Role
Description
The system shall allow an authorized administrator to remove an eligible permission from a role.
Priority
Must Have
Expected Result
Users receiving the affected permission through that role shall have their effective access recalculated according to the authorization model.
A user may still receive the same permission through another valid role.
Example:
USER │ ├── ROLE A ───► PATIENT_VIEW │ └── ROLE B ───► PATIENT_VIEW
Removing PATIENT_VIEW from Role A does not necessarily remove the user’s effective permission if Role B still provides it.

CS-IAM-FR-014 — Evaluate User Permission
Description
The system shall determine whether an authenticated user has the required permission before performing a protected operation.
Priority
Must Have
Main Requirement
For a protected operation:
REQUEST   │   ▼AUTHENTICATED?   │   ├──── NO ─────► REJECT   │   ▼  YES   │   ▼REQUIRED PERMISSION   │   ▼USER HAS EFFECTIVE PERMISSION?   │   ├──── NO ─────► DENY   │   ▼  YES   │   ▼CONTINUE TO BUSINESS RULES
Important Engineering Rule
Permission success does not automatically mean the business operation is valid.
Example:
A doctor may have:
PRESCRIPTION_CREATE
However, the doctor may still be prevented from prescribing in an invalid clinical context.
Therefore:
AUTHORIZATION      │      ▼BUSINESS VALIDATION      │      ▼DOMAIN OPERATION
not:
AUTHORIZATION      │      ▼AUTOMATIC SUCCESS
Acceptance Criteria
A protected operation shall not execute when the authenticated user lacks the required effective permission.

5.22 IAM REQUIREMENT RISKS
Risk 1 — Overly Simple Role Checking
A design based entirely on:
AdminUser
would be insufficient for CuraSphere.
Mitigation
Use role and business capability permission concepts.

Risk 2 — Frontend-Only Authorization
Hiding a React button is not sufficient security.
Example:
Button hidden
does not mean:
API protected
Mitigation
Protected business operations shall enforce authorization at the trusted backend boundary.

Risk 3 — Excessive Administrator Authority
A technical administrator may accidentally receive unrestricted clinical authority.
Mitigation
Separate:
SYSTEM ADMINISTRATION
from:
CLINICAL AUTHORITY

Risk 4 — Credential Exposure
Passwords or tokens may accidentally appear in:
logs;
API responses;
debugging output;
source code.
Mitigation
Sensitive authentication information shall be handled according to the security architecture.

Risk 5 — Stale Access
A deactivated user may retain an existing session.
Mitigation
The authentication architecture shall support applicable session revocation and account eligibility checks.
