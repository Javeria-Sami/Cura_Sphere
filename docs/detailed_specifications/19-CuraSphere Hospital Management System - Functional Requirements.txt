5.893 ADMINISTRATION DOMAIN BOUNDARY
The ADM/CFG module shall manage administrative configuration and shared reference data.
It shall not become the owner of every business entity in CuraSphere.
Example:
ADM/CFG MODULE      │      ▼OWNS DEPARTMENT MASTER DEFINITION
Department:
CARDIOLOGY
However:
HRM MODULE      │      ▼OWNS EMPLOYEE ASSIGNMENT
Example:
DOCTOR  │  ▼ASSIGNED TO CARDIOLOGY
Therefore:
DEPARTMENT MASTER DATA          ≠EMPLOYEE DEPARTMENT ASSIGNMENT
Another example:
ADM/CFG    │    ▼OWNS PAYMENT METHOD REFERENCE
Example:
CASHBANK TRANSFERCARD
Billing module:
BIL │ ▼OWNS PAYMENT TRANSACTION
Therefore:
PAYMENT METHOD      ≠PAYMENT
Another example:
ADM/CFG    │    ▼OWNS APPOINTMENT TYPE
Example:
INITIAL CONSULTATIONFOLLOW-UP CONSULTATION
Appointment module:
APT │ ▼OWNS APPOINTMENT
Therefore:
APPOINTMENT TYPE        ≠APPOINTMENT
Critical Principle
MASTER DATA     │     ▼DEFINES ALLOWED REFERENCE VALUE
BUSINESS MODULE       │       ▼USES REFERENCE VALUE
The Administration module shall not:
REGISTER PATIENTSCREATE APPOINTMENTSADMIT PATIENTSWRITE CLINICAL NOTESVERIFY LAB RESULTSFINALIZE RADIOLOGY REPORTSDISPENSE MEDICINESGENERATE INVOICESRECEIVE PAYMENTSAPPROVE LEAVEPROCESS SALARIES
It shall provide approved system configuration and shared reference data required by those modules.

5.894 CRITICAL CONFIGURATION ARCHITECTURE CONCEPT
CuraSphere shall distinguish:
APPLICATION CONFIGURATION
BUSINESS CONFIGURATION
MASTER DATA
SECRET
FEATURE FLAG
USER PREFERENCE
TRANSACTIONAL DATA
These concepts shall not be treated as identical.
Example application configuration:
MAXIMUM API REQUEST SIZEDEFAULT PAGE SIZEBACKGROUND WORKER INTERVAL
Business configuration:
APPOINTMENT CANCELLATION WINDOWINVOICE DUE PERIODLOW STOCK THRESHOLD POLICY
Master data:
DEPARTMENTSPECIALIZATIONPAYMENT METHODAPPOINTMENT TYPE
Secret:
DATABASE PASSWORDAPI SECRETPRIVATE KEYSIGNING KEY
Feature flag:
ENABLE_PATIENT_PORTAL_V2
User preference:
DARK MODEDASHBOARD LAYOUTLANGUAGE PREFERENCE
Transactional data:
PATIENTAPPOINTMENTINVOICEPAYMENT
Therefore:
CONFIGURATION      ≠MASTER DATA      ≠SECRET      ≠FEATURE FLAG      ≠USER PREFERENCE      ≠TRANSACTION
The architecture may provide controlled relationships between these concepts.

5.895 APPLICATION CONFIGURATION CONCEPT
Application configuration shall represent technical or application-level behavior settings.
Conceptually:
APPLICATION CONFIGURATION          │          ├── Configuration Key          ├── Configuration Value          ├── Data Type          ├── Category          ├── Default Value          ├── Validation Rule          ├── Environment Scope          ├── Hospital Scope          ├── Is Sensitive          ├── Is Runtime Changeable          ├── Is Cacheable          ├── Effective From          ├── Status          └── Version
Example:
CONFIGURATION KEYPagination.DefaultPageSizeVALUE25DATA TYPEINTEGERCATEGORYAPPLICATIONRUNTIME CHANGEABLEYES
Another example:
CONFIGURATION KEYAppointments.CancellationWindowHoursVALUE24DATA TYPEINTEGERCATEGORYAPPOINTMENT
Configuration keys shall use approved stable identifiers.
React display labels shall not become authoritative configuration keys.

5.896 MASTER DATA CONCEPT
Master data shall represent centrally managed reference values used by one or more CuraSphere business modules.
Conceptual model:
MASTER DATA     │     ├── Master Data ID     ├── Master Data Type     ├── Code     ├── Name     ├── Description     ├── Display Order     ├── Status     ├── Effective From     ├── Effective To     └── Additional Type-Specific Attributes
Example:
MASTER DATA TYPEPAYMENT_METHODCODECASHNAMECashSTATUSACTIVE
Another example:
MASTER DATA TYPEAPPOINTMENT_TYPECODEFOLLOW_UPNAMEFollow-Up ConsultationSTATUSACTIVE
Critical Principle
Master data codes shall be stable machine-readable values.
Example:
CODEFOLLOW_UP
Display name:
Follow-Up Consultation
Future display name:
Follow-Up Visit
The code may remain:
FOLLOW_UP
Therefore:
MASTER DATA CODE        ≠DISPLAY LABEL

5.915 ENVIRONMENT CONFIGURATION BOUNDARY
CS-ADM-FR-017 — Support Environment Configuration Boundary
The system shall distinguish runtime business configuration from environment and deployment configuration.
Environment examples:
DEVELOPMENTTESTINGSTAGINGPRODUCTION
Deployment configuration may include:
DATABASE CONNECTIONAPPLICATION HOSTLOGGING SINKTELEMETRY ENDPOINTSECRET PROVIDER
These values shall normally be managed through DevOps and secure deployment configuration.
They shall not automatically appear in the CuraSphere administration dashboard.
Therefore:
BUSINESS ADMIN CONFIGURATION             ≠DEVOPS ENVIRONMENT CONFIGURATION
Example:
Appointments.CancellationWindowHours
may be business configuration.
However:
PostgreSQL.Password
shall not be editable through a normal hospital administration UI.

5.917 CONFIGURATION VERSIONING

One version may represent the current effective value.
Configuration history shall not be implemented by silently overwriting all historical information.

Should Have

5.924 SECRET UI PROTECTION
CS-ADM-FR-026 — Prevent Secret Exposure in UI
The React administration application shall not display secret values.

Preferred:
DATABASE CREDENTIALCONFIGURED
or:

where approved.
Browser developer tools shall not receive secret values hidden only through CSS.
Incorrect architecture:
API RETURNS SECRET        │        ▼REACT HIDES SECRET
Preferred:

CS-ADM-FR-027 — Prevent Secret Exposure in API
The ASP.NET Core API shall not return secret values through normal administration endpoints.

The final secret administration workflow shall be defined during Security and DevOps Architecture.

5.991 ADMINISTRATION AND CONFIGURATION RISK ANALYSIS
Risk 1 — Every Setting Is Stored in One Configuration Table
Problem
Architecture:
settings├── key└── value
Everything is stored as text.
Impact
NO DATA TYPE SAFETYNO VALIDATIONNO SCOPENO VERSIONINGNO SENSITIVITY CLASSIFICATION
Mitigation
Define configuration metadata and typed validation.

Risk 2 — Secrets Stored with Normal Configuration
Problem
Database.Password
is stored beside:
Pagination.DefaultPageSize
Impact
Administrative users may access infrastructure secrets.
Mitigation
Separate secret management boundaries.

Risk 3 — React Receives Secrets and Hides Them
Problem
API returns:
SuperSecretPassword123
React displays:
********
Impact
The secret remains available in browser network tools.
Mitigation
Never return secret values to the browser.

Risk 4 — Configuration Change Has No Validation
Problem
Administrator sets:
Pagination.DefaultPageSize = 10000000
Impact
Application performance may degrade.
Mitigation
Apply configuration-specific validation.

Risk 5 — Configuration Change Is an SQL Update
Problem
Administrator or developer runs:
UPDATE settingsSET value = '0';
Impact
NO VALIDATIONNO VERSION HISTORYNO AUDITNO CACHE INVALIDATION
Mitigation
Use controlled configuration services and operational procedures.

Risk 6 — Cache Never Invalidates
Problem
Database:
Cancellation Window = 12
API server A:
24
API server B:
12
Impact
Users receive inconsistent system behavior.
Mitigation
Define cache invalidation and propagation strategy.

Risk 7 — Every Configuration Change Requires Deployment
Problem
Hospital wants to change:
Appointment Cancellation Window
Developer changes source code and redeploys production.
Impact
Operational configuration becomes tightly coupled to software deployment.
Mitigation
Identify approved runtime-managed business configuration.

Risk 8 — Every Technical Setting Is Editable in Admin UI
Problem
Hospital administrator changes:
DATABASE HOSTTOKEN SIGNING KEYTELEMETRY ENDPOINT
Impact
Security and production availability may be compromised.
Mitigation
Separate business administration configuration from DevOps configuration.

Risk 9 — Master Data and Transaction Data Are Mixed
Problem
Payment method record contains:
PAYMENT AMOUNTPATIENT IDINVOICE ID
Impact
Reference data and transactional data become tightly coupled.
Mitigation
Maintain clear domain boundaries.

Risk 10 — Master Data Is Hardcoded in React
Problem
const paymentMethods = [  "Cash",  "Card",  "Bank Transfer"];
Impact
Administrative changes require frontend deployment.
Mitigation
Load approved active reference data through backend contracts.

Risk 11 — Display Name Used as Database Meaning
Problem
Business logic:
if (paymentMethod.Name == "Cash")
Administrator renames:
Cash
to:
Cash Payment
Impact
Business logic fails.
Mitigation
Use stable codes.

Risk 12 — Master Data Code Can Be Freely Renamed
Problem
CASH
becomes:
CARD
Impact
Historical semantic meaning changes.
Mitigation
Apply stable code governance.

Risk 13 — Used Master Data Is Deleted
Problem
PAYMENT METHOD: CASH
is deleted.
Historical payments reference the deleted value.
Impact
Financial history becomes incomplete.
Mitigation
Use deactivation and dependency protection.

Risk 14 — Deactivation Removes Historical Meaning
Problem
Department is deactivated.
Old employee and appointment records no longer show the department.
Impact
Historical reporting becomes misleading.
Mitigation
Preserve historical references to inactive master data.

Risk 15 — Feature Flag Bypasses Authorization
Problem
ENABLE_ADMIN_PANEL = TRUE
causes all users to access the admin panel.
Impact
Authorization is bypassed.
Mitigation
Feature availability and user authorization shall remain separate.

Risk 16 — Configuration Restore Deletes History
Problem
Administrator restores Version 2.
Versions 3, 4, and 5 are deleted.
Impact
Configuration change history is lost.
Mitigation
Create a new version using the restored value.

Risk 17 — Configuration Import Directly Applies Changes
Problem
User uploads:
500 CONFIGURATION VALUES
The system immediately applies them.
Impact
One invalid value may disrupt multiple modules.
Mitigation
Validate and preview imports.

Risk 18 — Configuration Export Contains Secrets
Problem
Administrator exports:
ALL CONFIGURATION
File contains:
DATABASE PASSWORDAPI KEYSSIGNING SECRET
Impact
Critical credential leakage.
Mitigation
Exclude secrets from normal configuration exports.

Risk 19 — Generic Master Data Table Stores Complex Clinical Knowledge
Problem
All laboratory test definitions are stored as:
typecodenamevalue
Impact
Complex clinical rules become impossible to model correctly.
Mitigation
Use dedicated clinical domain models for complex knowledge.

Risk 20 — One Global Configuration for Every Hospital
Problem
Future Hospital B requires:
12 HOUR CANCELLATION WINDOW
Hospital A requires:
24 HOURS
Architecture supports only one global value.
Impact
Future hospital expansion requires major redesign.
Mitigation
Preserve a future configuration scope boundary.

Risk 21 — Full SaaS Multi-Tenancy Is Built Too Early
Problem
Initial CuraSphere deployment is for one hospital.
The development team builds:
COMPLEX TENANT SHARDINGCROSS-REGION TENANT ROUTINGTENANT BILLING PLATFORM
Impact
RAD development becomes unnecessarily complex.
Mitigation
Design extension boundaries without prematurely implementing full SaaS infrastructure.

Risk 22 — Missing Configuration Silently Returns Null
Problem
Code:
var value = config.Value;
Value:
NULL
Application continues.
Impact
Unpredictable runtime failures may occur later.
Mitigation
Use explicit configuration resolution and failure handling.

Risk 23 — Invalid Configuration Is Only Detected by Users
Problem
Configuration is invalid.
No health signal exists.
The first indication is:
PATIENT CANNOT BOOK APPOINTMENT
Impact
Operational disruption occurs before technical teams know the cause.
Mitigation
Implement configuration health verification.

Risk 24 — Admin Permission Grants All Business Permissions
Problem
System administrator automatically receives:
PATIENT RECORD ACCESSPAYMENT REVERSALSALARY APPROVAL
Impact
Administrative access becomes excessive.
Mitigation
Separate administration permissions from domain permissions.

Risk 25 — Master Data Usage Endpoint Exposes Sensitive Records
Problem
Master data administrator checks:
DEPARTMENT USAGE
and receives complete patient records.
Impact
Source-domain authorization is bypassed.
Mitigation
Return usage summaries rather than unauthorized source records.
