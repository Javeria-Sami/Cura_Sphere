2.2 Product Perspective
CuraSphere is a centralized, web-based Hospital Management System.
The product shall provide a common digital platform through which authorized hospital users can perform clinical, administrative, operational, and financial activities.
CuraSphere shall be designed as an independent software product.
The initial system shall target a single healthcare organization while maintaining an architectural direction that allows future support for:
multiple hospital branches;
multiple healthcare facilities;
specialized clinics;
diagnostic centers;
hospital groups;
cloud-hosted healthcare services.
CuraSphere shall not initially be designed as a collection of independent microservices.
The initial product shall use a modular application architecture.
The application shall maintain clear module and layer boundaries to reduce unnecessary technical complexity during initial development.
The initial architectural perspective is:
                         CURASPHERE                    ┌───────────────────┐                    │    Web Client     │                    │     React.js      │                    └─────────┬─────────┘                              │                              │ HTTPS                              │ REST API                              ▼                    ┌───────────────────┐                    │   ASP.NET Core    │                    │    Application    │                    └─────────┬─────────┘                              │                   ┌──────────┼──────────┐                   │          │          │                   ▼          ▼          ▼               Domain     Application  Infrastructure                Rules       Services      Services                   │          │          │                   └──────────┼──────────┘                              │                              ▼                    ┌───────────────────┐                    │    PostgreSQL     │                    │     Database      │                    └───────────────────┘
The detailed architectural decisions shall be defined in the Software Architecture Document.
The SRS only defines architectural constraints that are directly related to system requirements.

2.3 Product Positioning
CuraSphere is positioned between hospital users and hospital information.
Without an integrated hospital management platform, hospital departments may directly manage their own records.
Example:
Reception ───────► Patient FilesDoctor ──────────► Clinical NotesLaboratory ──────► Laboratory RecordsPharmacy ────────► Medicine RecordsBilling ─────────► Financial Records
This creates separate information systems.
CuraSphere introduces a controlled application layer.
                     HOSPITAL USERS        Receptionist    Doctor       Nurse        Pharmacist      Lab Staff    Accountant        Administrator   Management   IT Support                           │                           ▼                 ┌──────────────────────┐                 │                      │                 │      CURASPHERE      │                 │                      │                 │ Authentication       │                 │ Authorization        │                 │ Business Rules       │                 │ Validation           │                 │ Workflow Control     │                 │ Audit Logging        │                 │                      │                 └───────────┬──────────┘                             │                             ▼                 ┌──────────────────────┐                 │  HOSPITAL DATA       │                 │                      │                 │ Patients             │                 │ Medical Records      │                 │ Appointments         │                 │ Laboratory           │                 │ Pharmacy             │                 │ Billing              │                 │ Inventory            │                 │ Staff                │                 └──────────────────────┘
Users shall not directly access the primary production database for normal hospital operations.
Hospital activities shall be performed through authorized CuraSphere interfaces or approved system integrations.

2.9 Operating Environment
CuraSphere shall operate as a web-based application.
2.9.1 Client Environment
The primary client shall be a modern web browser.
Supported browser categories should include current supported versions of:
Chromium-based browsers;
Microsoft Edge;
Mozilla Firefox.
Safari support may be validated according to deployment requirements.
The user interface shall be implemented using React.js.
The detailed frontend technology version shall be fixed during architecture baseline creation.

2.9.2 Server Environment
The backend shall use the .NET platform and C#.
The server application shall expose controlled APIs to approved clients.
The preferred backend application model is:
ASP.NET Core Web API
The exact supported .NET version shall be selected as an actively supported release during architecture implementation.
The production system shall not depend on an unsupported runtime version.

2.9.3 Database Environment
PostgreSQL shall be the primary relational database management system.
The database shall store structured CuraSphere application information.
The system shall use controlled application access to the database.
Normal users shall not directly connect to PostgreSQL.
The expected database flow is:
USER  │  ▼REACT APPLICATION  │  ▼ASP.NET CORE API  │  ▼APPLICATION RULES  │  ▼DATA ACCESS  │  ▼POSTGRESQL

2.9.4 Development Environment
The primary backend development environment shall support:
Visual Studio;
.NET development;
C# development;
debugging;
testing.
Frontend development may use:
Visual Studio Code;
Node.js development tools;
React development tools.
The project shall use Git for source version control.

2.10 Design and Implementation Constraints
The following constraints apply to the initial CuraSphere project.
CS-SYS-CON-001 — Frontend Technology
The primary web frontend shall use React.js.
CS-SYS-CON-002 — Backend Technology
The backend application shall use C# and the .NET platform.
CS-SYS-CON-003 — Backend Application Framework
The primary backend API shall use ASP.NET Core.
CS-SYS-CON-004 — Database Technology
The primary relational database shall use PostgreSQL.
CS-SYS-CON-005 — API Communication
The web client shall communicate with the backend through approved HTTP-based APIs.
Production communication shall use HTTPS.
CS-SYS-CON-006 — Database Access
Normal application users shall not directly access the production database.
CS-SYS-CON-007 — Authentication
Protected application functions shall require authenticated access.
CS-SYS-CON-008 — Authorization
Protected operations shall be controlled by authorization rules.
CS-SYS-CON-009 — Auditability
Security-sensitive and selected business-sensitive activities shall be auditable.
CS-SYS-CON-010 — Version Control
Application source code and approved technical configuration shall be maintained through Git-based version control.
CS-SYS-CON-011 — Environment Separation
The project shall maintain logically separate development and production environments.
A test or staging environment should be maintained before production release.
CS-SYS-CON-012 — Secret Management
Passwords, database credentials, token secrets, and other sensitive secrets must not be hardcoded into source code.
CS-SYS-CON-013 — Modular Design
The application shall maintain identifiable functional module boundaries.
CS-SYS-CON-014 — Maintainability
Implementation shall follow documented naming, structure, and coding conventions.
CS-SYS-CON-015 — Browser-Based Access
The initial hospital staff interface shall be browser based.

SECTION 2 SUMMARY
Section 2 establishes that CuraSphere is:
a web-based Hospital Management System;
an integrated hospital information platform;
built around controlled information access;
designed for clinical, administrative, operational, and financial workflows;
initially targeted at a single hospital;
designed with future scalability in mind;
based on React.js for the frontend;
based on C# and ASP.NET Core for the backend;
based on PostgreSQL for relational data storage;
designed for container-compatible deployment;
based on modular system boundaries;
accessed by multiple hospital user classes;
integrated with external services only through controlled interfaces.
