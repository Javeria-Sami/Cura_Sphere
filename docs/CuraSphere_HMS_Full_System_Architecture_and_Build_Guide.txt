1. PRODUCT BASELINE
The original CuraSphere vision describes a centralized HMS connecting clinical, administrative, financial, inventory and reporting operations. Its stated included scope covers patient registration, medical records, OPD, IPD, emergency, ICU, surgery, nursing, staff/user/department management, scheduling, attendance, billing, payments, insurance, pharmacy, medical supplies, equipment and management reports. fileciteturn4file17L1-L15
1.1 Core Product
CuraSphere├── Clinical├── Administrative├── Financial├── Inventory├── Reporting├── Notifications├── Security / Audit└── System Administration
1.2 Product Principle
One patient record, one controlled workflow, shared authorized data, complete auditability.
1.3 Original Success Targets
Reduce registration time and manual work.
Streamline appointment scheduling.
Minimize billing errors.
Track medicine and supply inventory accurately.
Share consistent data across departments.
Provide operational reports and management visibility.
Maintain security and availability.
These success criteria are part of the original project vision. fileciteturn4file0L1-L15

3.1 Architecture Rules
Frontend never connects directly to PostgreSQL.
Backend owns business rules.
Database owns persistence and transaction integrity.
Sensitive actions require authorization and auditing.
Real-time events are emitted after successful persistence.
Server state belongs in TanStack Query rather than duplicating it in Zustand.
These rules are consistent with the current CuraSphere build blueprint. fileciteturn4file12L1-L14

Show loading state and prevent duplicate submission.

8.2 Backend
Receive login request.
Validate credentials using Identity.
Create access/session response.
Apply lockout/rate-limit policy where appropriate.
Return user identity and permissions needed by the client.

51. FINAL ENGINEERING RULES
The database is the source of truth.
Business rules are enforced on the backend.
Frontend never accesses PostgreSQL directly.
Use TanStack Query for server state.
Use Zustand for appropriate client/UI state.
Use transactions for critical multi-step operations.
Clinical and financial history must be protected from silent modification.
Every sensitive action must be authorized and auditable.
Real-time events happen after successful persistence.
Secrets never enter Git.
Every major feature is built as UI + database + API + tests.
Do not mark a feature complete until its workflow, error states and permissions are tested.
52. FINAL BUILD DEFINITION
CuraSphere is complete when the team can demonstrate the full patient journey in a working environment, with each authorized department seeing the correct information, each critical transaction persisted correctly, sensitive actions audited, real-time operational updates functioning where required, and the system passing its automated and user acceptance tests.
The original project vision identifies the broader goal as a reliable, secure, scalable digital healthcare platform that improves communication, reduces manual work, supports patient care and provides accurate real-time data. fileciteturn4file6L1-L15
This document therefore becomes the master implementation blueprint alongside the SRS: the SRS defines requirements, while this document defines the practical route from requirement → design → code → database → API → testing → deployment.
